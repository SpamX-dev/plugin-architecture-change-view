# ArchiView

ArchiView показывает, какие модули изменились в Git, что обещают их контракты и для какого состояния кода выполнена архитектурная проверка.

## Локальный запуск

Нужны Git и Node.js 22.23.4 или новее. Команды для запуска из каталога ArchiView приведены ниже.

```sh
npm ci
npm start -- --root .
```

Откройте `http://127.0.0.1:4317`. В `--root` можно передать путь к другому Git-репозиторию или папке с несколькими репозиториями. Порт задаётся через `--port`. Данные проекта по умолчанию сохраняются в его каталоге `.archiview`.

Для переноса на другую машину выполните `npm run build`, скопируйте `dist/` и запустите `node dist/cli.mjs --root ПУТЬ`. Сборка включает CLI, веб-интерфейс и инструкции для анализа. На машине запуска достаточно Git и Node.js.

Для установки ArchiView в профиль текущего пользователя выполните `npm run install:user` после `npm ci`. Команда собирает приложение, устанавливает автономную копию в `~/.archiview/npm` и выводит путь запуска. В Windows запускайте `~/.archiview/npm/archiview.cmd --root ПУТЬ`, в Linux и macOS — `~/.archiview/npm/bin/archiview --root ПУТЬ`. Повторная установка обновляет копию из рабочего дерева.

## Работа в браузере

На вкладке «Связи» видны прямые зависимости на один шаг в обе стороны. Если модуль A импортирует B, а B реэкспортирует тип из C, в карточке A появится B. Связь с C можно раскрыть в карточке B. Учитываются также импорты типов TypeScript и JSDoc. Для `import()`, `require()` и загрузчика Node.js, созданного через `createRequire(import.meta.url)` в этом модуле, укажите путь строковым литералом или шаблоном без подстановок. Например, ArchiView распознаёт `import(("./api.js" as const))` и `const load = createRequire(import.meta.url); load("./api.cjs")`. По каждой связи доступны исходные строки выбранного снимка.

Кнопка «Построить связи проекта» запускает поставляемый с ArchiView индексатор TypeScript/JavaScript для всего выбранного репозитория. Для разрешения импортов используются конфигурация проекта и его установленные зависимости. Результаты хранятся в каталоге состояния под `snapshots/relations/`. Построение из CLI — `archiview --build-relations`, чтение — `archiview --module-relations ID`.

Голубой жук в дереве и на вкладке «Реализация» отмечает циклические зависимости выбранного снимка. Цепочки и места использования можно посмотреть в разделе «Циклические зависимости» на этой вкладке.

Выберите репозиторий, состояние Git и модуль в дереве. В карточке доступны контракт, собственные файлы с diff и актуальные результаты проверок композиции и реализации. Можно сохранить именованный снимок, открыть предыдущую версию, отредактировать пункт контракта или восстановить его из базовой версии. Прототипы с привязкой к каталогу можно создать до появления исходников. При изменениях в рабочей папке открытый просмотр обновляется.

## CLI

Команды можно выполнять из исходников через `npm run archiview --` или из сборки через `node dist/cli.mjs`. Эти примеры читают данные самого ArchiView.

```sh
node dist/cli.mjs --root . --list-modules
node dist/cli.mjs --root . --module-files archiview-cli --target index
node dist/cli.mjs --root . --get-contract archiview-cli
```

Чтобы обновить контракт, передайте `--write-contract ID --input FILE.yaml`. При первой регистрации добавьте `--directory DIR`. Для рабочей папки с несколькими репозиториями укажите `--repository` с путём из списка. Для чтения доступны `current`, `index` и `git-<полный хеш коммита>`.

Команда `--inventory` показывает покрытие исходных каталогов контрактами, `--module-context PATH` выводит цепочку контрактов, а `--scaffold PLAN.yaml` создаёт прототипы из плана. Все команды, включая экспорт, импорт, построение отчётов и проверку индекса Git, перечислены в `--help`.

## Проверки

`npm test` собирает приложение и запускает тесты модулей, Git, HTTP и CLI на временных репозиториях. `npm run test:web` запускает браузерные сценарии. Для них нужен Chromium от Playwright (`npx playwright install chromium`) или совместимый браузер по пути `ARCHIVIEW_CHROMIUM_PATH`. В Windows также обнаруживаются установленные Chrome и Edge.

## Структура

Каталоги повторяют отношения вложенности на [схеме архитектуры](docs/architecture.svg).

```text
tools/
builds/
skills/
  module-boundaries/
test/
web/
  web-ui/
    workspace-presenter/
    module-presenter/
    views/
    archiview-client/
  web-backend/
    file-service/
    file-watcher/
    web-service/
    analysis-service/
    runtime/
    host-bridge/
bridges/
  codex/
  dsh/
cli/
module-operations/
storage/
analyse/
  project/
    project-files/
  project-sources/
  git-changes/
  module-review/
framework/
  ai-report/
  static-report/
  contracts/
  snapshots/
  project/
  project-types/
  serialization/
```

`[Analyse-type]` на схеме описывает структуру будущих модулей анализа. При добавлении конкретного вида анализа в `analyse/` создают его именованный каталог и контракт. Если анализ формирует отчёт, файл с кодом его записи и чтения входит в этот же модуль.

`analyse/git-changes` описывает сравнение файлов между выбранными состояниями Git. Например, сравнение `HEAD` с индексом показывает изменения, подготовленные к коммиту, а сравнение индекса с рабочим деревом — изменения после подготовки и новые неигнорируемые файлы. Результат такого сравнения сохраняется в виде отчёта.

`archiview --save-comparison --baseline index --target current` сохраняет сравнение индекса с рабочим деревом и выводит ID. Команда `archiview --read-comparison ID` возвращает зафиксированную пару состояний и список изменений даже после новых правок. Отчёты хранятся в `.archiview/comparisons/`. При переносе скопируйте этот каталог вместе с `.archiview/project.json`. Команда `--build-report` также выводит ID сохранённого сравнения.

Каталоги `analyse/project/project-files` и `web/web-backend/file-service` зарезервированы на схеме. В текущей реализации за списком и содержимым файлов выбранного состояния обращаются через `module-operations`. Узел `?` в Framework оставлен открытым до определения его назначения.

## Вкладки анализа модуля

В карточке модуля каждому виду анализа отводится своя вкладка. На ней пользователь видит проверки и замечания этого вида для выбранного среза. Завершённый результат остаётся актуальным, пока сохраняются его входы. Когда актуального результата нет, на самой вкладке доступна кнопка «Выполнить анализ». Для новых видов анализа можно добавлять вкладки со своими входами и правилами проверки.

| Вкладка | Входы из выбранного среза | Что проверяем |
|---|---|---|
| **Композиция** | Собственный контракт модуля, состав непосредственных детей и их контракты | Позволяет ли распределение обязанностей между детьми выполнить обещание родителя с учётом его границ и инвариантов? |
| **Реализация** | Собственный контракт модуля и принадлежащие ему исходные файлы | Выполняет ли код заявленное назначение, соблюдает ли границы и инварианты? Выводы по пунктам контракта опираются на конкретные места в коде. |

На вкладке **Реализация** также доступна статическая проверка циклических зависимостей по графу TypeScript / JavaScript выбранного снимка. Для каждой исходящей связи, из которой есть путь обратно к выбранному модулю, показана одна кратчайшая замкнутая цепочка и место использования на каждом переходе. Учитываются и импорты типов. Цепочки доступны независимо от наличия отчёта агента. Если граф рабочего дерева ещё не построен, нажмите **Построить связи проекта** на этой же вкладке. Для исторического снимка используется его сохранённый граф.

При проверке композиции роль ребёнка определяется относительно задачи родителя. Для **непосредственных исполнителей** проверяем, совместимы ли их обещания друг с другом и с контрактом родителя и обеспечивают ли они вместе обещанный результат. Для **утилиты** определяем, кому и для какой задачи она нужна в этой композиции. Затем проверяем, достаточен ли её контракт для этой задачи и укладываются ли в неё все обязанности утилиты.

Файл `.archiview/work/<key>.analysis.yaml` модуля хранит по одному результату **композиции** и **реализации** вместе с их доказательствами. Новый результат обновляет запись своего вида. Общий отчёт, созданный через CLI, использует отдельную запись `generic`. У замечания можно изменить статус и решение. Они сохраняются отдельно от отчёта. Доступны статусы «Открыто», «Принято» и «Закрыто». Счётчик на вкладке показывает открытые замечания.

Историю отчётов хранит Git. Чтобы сохранить версию, включите файл модуля из `.archiview/work/` в коммит. При выборе коммита ArchiView читает файл результатов версии 3 из этого коммита и проверяет применимость отчёта к выбранному коду. В коммите с прежним форматом вкладка показывает отсутствие результата. Если между двумя коммитами выполнить несколько анализов одного вида, в следующий коммит попадёт версия, добавленная в индекс. [Формат отчётов](docs/report-format-v2.md)

Например, при добавлении кеша к модулю облачного хранения заново проверяется композиция родителя. Если родитель обещает сохранение в облаке к моменту ответа, а контракты детей вместе гарантируют только локальную запись к этому моменту, замечание появится на вкладке «Композиция». Если контракт родителя обещает ждать подтверждения облака, а его собственный код возвращает успех сразу после записи в кеш, замечание появится на вкладке «Реализация».

Изменение собственного контракта требует повторить оба вида анализа модуля и проверить композицию его непосредственного родителя. Добавление или удаление ребёнка меняет входы проверки композиции родителя. Правка только собственного кода требует повторить «Реализацию» у владельца кода. Например, в дереве `A → B → C` правка контракта `C` требует пересмотреть композицию `B`. До `A` изменение дойдёт, если при этом изменится контракт `B`.

## Доменная модель ArchiView

Framework задаёт структуру и смысл доменных данных. Например, `framework/contracts` описывает поля контракта модуля и его связь с записью в `modules.tree`. Идентификатор в документе должен совпадать с идентификатором в карте. Для отчётов Framework задаёт, какие выводы и доказательства они могут содержать. Факты о репозитории собирают модули анализа.

## Веб-бэкенд

В `web/web-backend` модуль `web-service` обслуживает HTTP-запросы, а `file-watcher` предоставляет события об изменениях файловой системы через уведомления ОС. Сессия выбранного репозитория использует их для обновления дерева и состояния отчётов.

## Обнаружение и выбор проекта

`analyse/project` обследует рабочую папку и возвращает найденные Git-репозитории. Для каждого он указывает, есть ли в нём карта `.archiview/modules.tree`. Например, если `client/` и `server/` — отдельные репозитории, а карта есть только в `client/`, в списке будут оба.

`analyse/project-sources` читает файлы репозитория и его карту, составляет инвентаризацию модулей и находит цепочку контрактов для выбранного пути. Хранилища снимков и отчётов используют `storage/` для проверки происхождения архива, безопасного доступа к файлам состояния и блокировки параллельных записей.

Контекст выбранного репозитория описан в `framework/project`. В нём заданы корень, правила принадлежности путей и допустимое расположение архитектурных данных. Карта модулей необязательна, поэтому `server/` можно выбрать и изучать до её создания. Общие типы данных проекта описаны в `framework/project-types`.

## Операции с модулями

CLI разбирает аргументы команды и выводит результат. В веб-бэкенде `web-service` принимает HTTP-запрос и формирует ответ. Оба передают запрос и контекст выбранного репозитория в `module-operations`. Этот прикладной модуль читает файлы, проверяет контракты по правилам доменной модели и записывает изменения.

| Действие | Что предоставляет общая операция |
| --- | --- |
| Список модулей | Идентификаторы и каталоги модулей выбранного репозитория. |
| Файлы модуля | Список собственных файлов выбранного модуля в указанном состоянии проекта. |
| Чтение контракта | Контракт выбранного модуля в том же состоянии проекта. |
| Запись контракта | Создание контракта с привязкой к каталогу или обновление существующего контракта по ID в рабочем дереве. |

`framework/contracts` задаёт формат карты и контрактов, `framework/snapshots` — представление файлов в снимке.

## Анализ модуля

Выберите вкладку **Композиция** или **Реализация** в карточке модуля. Если для выбранного среза требуется проверка, раскройте **Выполнить анализ ▾**. Меню запрашивает работающие локальные мосты. Выбор Codex или DeepSeek Harness создаёт новый чат с поручением по выбранному снимку. Сначала мост ищет проект по корню Git-репозитория, затем по рабочей папке ArchiView. DeepSeek Harness также умеет запустить чат в каталоге репозитория. Для Codex Desktop требуется соответствующий локальный проект.

Агент получает сохранённые входы, записывает `result.yaml` и выполняет `--complete-analysis REQUEST_ID`. Карточка показывает подтверждение доставки и обновляет результаты после импорта ожидаемого отчёта. При потере подтверждения проверьте чат в выбранном хосте перед запуском ещё одного анализа. Пункт **Копировать промпт** позволяет передать те же входы вручную.

У замечания на вкладке соответствующего анализа кнопка **Исправить ▾** открывает список подключённых harness. Выбранный хост получает поручение по конкретному замечанию в новом чате проекта. В этом же меню можно скопировать поручение.

### Подключение Codex Desktop

После `npm run build` добавьте stdio-сервер в пользовательский `~/.codex/config.toml`. Укажите абсолютный путь к собранному файлу. В Windows можно использовать прямые слеши.

```toml
[mcp_servers.archiview-harness]
command = "node"
args = ["/absolute/path/to/dist/bridges/codex/server.mjs"]
env_vars = ["CODEX_APP_TOOLS_PIPE_PATH", "CODEX_APP_TOOLS_CALLER_HOST_ID", "CODEX_THREAD_ID"]
```

Откройте локальный чат в Codex Desktop и попросите вызвать `archiview_connect`. Это привяжет мост к запущенному Desktop. При запуске из терминала агента с контекстом Codex ту же привязку выполняет `node /absolute/path/to/dist/bridges/codex/server.mjs --connect`. Дальнейшие запросы из ArchiView создают отдельные чаты в выбранном проекте. Если Desktop сменил канал при перезапуске, повторите подключение.

### Подключение DeepSeek Harness

Выполните `dsh plugin --profile desktop add /absolute/path/to/dist/bridges/dsh`. Cordis регистрирует мост при активации плагина. Если профиль ещё не подхватил изменение, перезапустите профиль. Для Web-профиля укажите `--profile web`.

ArchiView и оба хоста должны работать под одним локальным пользователем и иметь доступ к файлам проекта. Мосты публикуют регистрацию в `~/.archiview/harnesses`, backend проверяет доступность по локальному IPC перед показом меню и отправкой. Переменная `ARCHIVIEW_BRIDGE_DIR` задаёт общий альтернативный каталог для изолированного запуска.

### Автопроверка изменений агента

В панели ArchiView откройте **Настройки** выбранного репозитория. Включите **Автоанализ изменений**, а для работы в Codex также **Подключить хуки Codex**. Изменения сохраняются сразу. Если панель показывает запрос доверия, подтвердите команды ArchiView через `/hooks` в Codex. После настройки панель можно закрыть.

При ручной настройке включите анализ в `.archiview/agent-review.json` значением `{"enabled":true}`.

Для Codex добавьте обработчики в `.codex/hooks.json` доверенного проекта или в пользовательский `~/.codex/hooks.json`. Замените путь на абсолютный путь к собранному `cli.mjs`. В существующем файле добавьте записи к соответствующим событиям. После изменения подтвердите новые команды в списке хуков Codex. [Справочник хуков Codex](https://developers.openai.com/codex/hooks)

```json
{
  "hooks": {
    "UserPromptSubmit": [
      {"hooks": [{"type": "command", "command": "node \"/path/to/dist/cli.mjs\" --turn-hook codex"}]}
    ],
    "Stop": [
      {"hooks": [{"type": "command", "command": "node \"/path/to/dist/cli.mjs\" --turn-hook codex"}]}
    ]
  }
}
```

Для DeepSeek Harness добавьте обработчик в `cordis.patch.yml` профиля с установленным мостом ArchiView и перезапустите профиль. Он принимает события чатов в указанном репозитории и его подкаталогах. Обе команды выполняются с политикой доступа текущей сессии. На Windows используйте `node.exe` для запуска системного Node.js.

```yaml
- insert:
    - id: archiview-turn-hooks
      name: archiview-harness-bridge/session-hooks.mjs
      config:
        repository: /absolute/path/to/project
        command: 'node "/absolute/path/to/dist/cli.mjs" --turn-hook dsh --root "/absolute/path/to/project"'
```

По умолчанию хук выбирает Git-репозиторий текущего каталога. Для чата, открытого в папке над репозиторием, добавьте `--root /путь/к/репозиторию` в обе команды. Для внешнего хранилища добавьте одинаковый `--state-dir`.

На `UserPromptSubmit` ArchiView передаёт агенту инструкцию `module-boundaries`. После правок и тестов агент вызывает `--review-current`. Команда возвращает модули, которым сейчас нужна проверка композиции, проверка реализации или исправление открытых замечаний. Агент готовит задания через `--prepare-current-review MODULE_ID --analysis-type composition|implementation` и запускает анализ и исправления подагентами в этом же чате. После импорта результатов и исправления подтверждённых проблем агент повторяет проверку текущего состояния.

Поле `relations` в ответе показывает, нужен ли актуальный SCIP-граф TS/JS или разбор уже построенного графа. Агент строит отсутствующий граф через `--build-relations`, передаёт подагенту данные `--relation-review-input` и сохраняет его отчёт через `--complete-relation-review FILE`. В разбор входят прямые связи, циклы, соответствие контрактам и исходные места использования. `relations.findings` включает обнаруженные циклы между модулями и замечания из сохранённого отчёта о связях. Агент исправляет их вместе с замечаниями к модулям после анализа, затем проверяет актуальность графа и отчётов.

На `Stop` CLI заново проверяет анализы модулей и состояние связей. Если осталось построить или разобрать граф либо есть открытые замечания, хук один раз просит продолжить работу в этом же ходе. Автопроверка работает через CLI и подагентов. Мосты используются при ручной отправке заданий из панели. Установите `enabled` в `false`, чтобы отключить автопроверку проекта.

## Прототипы модулей

[Карта модулей](.archiview/modules.tree) связывает устойчивые идентификаторы с каталогами. В [контрактах](.archiview/modules) записаны назначение, роль и границы каждого модуля. У проектируемых модулей выставлен признак `archiview.prototype: true`. В пустых конечных каталогах лежит `.gitkeep`, чтобы Git воспроизводил структуру при клонировании.

Скилл [module-boundaries](skills/module-boundaries/SKILL.md) содержит правила ведения контрактов. Документы о панелях Codex и DSH в `docs/` описывают предыдущую реализацию.
