# ArchiView

ArchiView показывает, какие модули изменились в Git, что обещают их контракты и для какого состояния кода выполнена архитектурная проверка.

## Локальный запуск

Нужны Git и Node.js 22.23.4 или новее. Команды для запуска из каталога ArchiView приведены ниже.

```sh
npm ci
npm start -- --root .
```

Откройте `http://127.0.0.1:4317`. В `--root` можно передать путь к другому Git-репозиторию или папке с несколькими репозиториями. Порт задаётся через `--port`. Данные проекта по умолчанию сохраняются в его каталоге `.archiview`.

Для переноса на другую машину выполните `npm run build`, скопируйте `dist/` и запустите `node dist/cli.mjs --root ПУТЬ`. Сборка включает CLI, веб-интерфейс и инструкции для анализа. На машине запуска достаточно Git и Node.js.

## Работа в браузере

На вкладке «Связи» видны прямые зависимости на один шаг в обе стороны. Если модуль A импортирует B, а B реэкспортирует тип из C, в карточке A появится B. Связь с C можно раскрыть в карточке B. Учитываются также импорты типов и распознанные индексатором вызовы `import()` и `require()` со строковым путём. По каждой связи доступны исходные строки выбранного снимка.

Кнопка «Построить связи проекта» запускает поставляемый с ArchiView индексатор TypeScript/JavaScript для всего выбранного репозитория. Для разрешения импортов используются конфигурация проекта и его установленные зависимости. Результаты хранятся в каталоге состояния под `snapshots/relations/`. Построение из CLI — `archiview --build-relations`, чтение — `archiview --module-relations ID`.

Выберите репозиторий, состояние Git и модуль в дереве. В карточке доступны контракт, собственные файлы с diff и результаты последней проверки. Можно сохранить именованный снимок, открыть предыдущую версию, отредактировать пункт контракта или восстановить его из базовой версии. Прототипы с привязкой к каталогу можно создать до появления исходников. При изменениях в рабочей папке открытый просмотр обновляется.

## CLI

Команды можно выполнять из исходников через `npm run archiview --` или из сборки через `node dist/cli.mjs`. Эти примеры читают данные самого ArchiView.

```sh
node dist/cli.mjs --root . --list-modules
node dist/cli.mjs --root . --module-files archiview-cli --target index
node dist/cli.mjs --root . --get-contract archiview-cli
```

Чтобы обновить контракт, передайте `--write-contract ID --input FILE.yaml`. При первой регистрации добавьте `--directory DIR`. Для рабочей папки с несколькими репозиториями укажите `--repository` с путём из списка. Для чтения доступны `current`, `index` и `git-<полный хеш коммита>`.

Команда `--inventory` показывает покрытие исходных каталогов контрактами, `--module-context PATH` выводит цепочку контрактов, а `--scaffold PLAN.yaml` создаёт прототипы из плана. Все команды, включая экспорт, импорт, построение отчётов и проверку индекса Git, перечислены в `--help`.

## Проверки

`npm test` собирает приложение и запускает тесты модулей, Git, HTTP и CLI на временных репозиториях. `npm run test:web` запускает браузерные сценарии. Для них нужен Chromium от Playwright (`npx playwright install chromium`) или совместимый браузер по пути `ARCHIVIEW_CHROMIUM_PATH`. В Windows также обнаруживаются установленные Chrome и Edge.

## Структура

Каталоги повторяют отношения вложенности на [схеме архитектуры](docs/architecture.svg).

```text
tools/
builds/
skills/
  module-boundaries/
test/
web/
  web-ui/
    workspace-presenter/
    module-presenter/
    views/
    archiview-client/
  web-backend/
    file-service/
    file-watcher/
    web-service/
    analysis-service/
    runtime/
    host-bridge/
bridges/
  codex/
  dsh/
cli/
module-operations/
analyse/
  project/
    project-files/
  git-changes/
  module-review/
framework/
  ai-report/
  static-report/
  contracts/
  snapshots/
  project/
  project-types/
  serialization/
```

`[Analyse-type]` на схеме описывает структуру будущих модулей анализа. При добавлении конкретного вида анализа в `analyse/` создают его именованный каталог и контракт. Если анализ формирует отчёт, файл с кодом его записи и чтения входит в этот же модуль.

`analyse/git-changes` описывает сравнение файлов между выбранными состояниями Git. Например, сравнение `HEAD` с индексом показывает изменения, подготовленные к коммиту, а сравнение индекса с рабочим деревом — изменения после подготовки и новые неигнорируемые файлы. Результат такого сравнения сохраняется в виде отчёта.

`archiview --save-comparison --baseline index --target current` сохраняет сравнение индекса с рабочим деревом и выводит ID. Команда `archiview --read-comparison ID` возвращает зафиксированную пару состояний и список изменений даже после новых правок. Отчёты хранятся в `.archiview/comparisons/`. При переносе скопируйте этот каталог вместе с `.archiview/project.json`. Команда `--build-report` также выводит ID сохранённого сравнения.

Каталоги `analyse/project/project-files` и `web/web-backend/file-service` зарезервированы на схеме. В текущей реализации за списком и содержимым файлов выбранного состояния обращаются через `module-operations`. Узел `?` в Framework оставлен открытым до определения его назначения.

## Доменная модель ArchiView

Framework задаёт структуру и смысл доменных данных. Например, `framework/contracts` описывает поля контракта модуля и его связь с записью в `modules.tree`. Идентификатор в документе должен совпадать с идентификатором в карте. Для отчётов Framework задаёт, какие выводы и доказательства они могут содержать. Факты о репозитории собирают модули анализа.

## Веб-бэкенд

В `web/web-backend` модуль `web-service` обслуживает HTTP-запросы, а `file-watcher` предоставляет события об изменениях файловой системы через уведомления ОС. Сессия выбранного репозитория использует их для обновления дерева и состояния отчётов.

## Обнаружение и выбор проекта

`analyse/project` обследует рабочую папку и возвращает найденные Git-репозитории. Для каждого он указывает, есть ли в нём карта `.archiview/modules.tree`. Например, если `client/` и `server/` — отдельные репозитории, а карта есть только в `client/`, в списке будут оба.

Контекст выбранного репозитория описан в `framework/project`. В нём заданы корень, правила принадлежности путей и допустимое расположение архитектурных данных. Карта модулей необязательна, поэтому `server/` можно выбрать и изучать до её создания. Общие типы данных проекта описаны в `framework/project-types`.

## Операции с модулями

CLI разбирает аргументы команды и выводит результат. В веб-бэкенде `web-service` принимает HTTP-запрос и формирует ответ. Оба передают запрос и контекст выбранного репозитория в `module-operations`. Этот прикладной модуль читает файлы, проверяет контракты по правилам доменной модели и записывает изменения.

| Действие | Что предоставляет общая операция |
| --- | --- |
| Список модулей | Идентификаторы и каталоги модулей выбранного репозитория. |
| Файлы модуля | Список собственных файлов выбранного модуля в указанном состоянии проекта. |
| Чтение контракта | Контракт выбранного модуля в том же состоянии проекта. |
| Запись контракта | Создание контракта с привязкой к каталогу или обновление существующего контракта по ID в рабочем дереве. |

`framework/contracts` задаёт формат карты и контрактов, `framework/snapshots` — представление файлов в снимке.

## Анализ модуля

Откройте карточку модуля и раскройте **Анализировать ▾**. Меню запрашивает работающие локальные мосты. Выбор Codex или DeepSeek Harness создаёт новый чат с поручением по выбранному снимку. Сначала мост ищет проект по корню Git-репозитория, затем по рабочей папке ArchiView. DeepSeek Harness также умеет запустить чат в каталоге репозитория. Для Codex Desktop требуется соответствующий локальный проект.

Агент получает сохранённые входы, записывает `result.yaml` и выполняет `--complete-analysis REQUEST_ID`. Карточка показывает подтверждение доставки и обновляет результаты после импорта ожидаемого отчёта. При потере подтверждения проверьте чат в выбранном хосте перед запуском ещё одного анализа. Пункт **Копировать промпт** позволяет передать те же входы вручную.

На вкладке «Замечания» кнопка **Исправить ▾** открывает список подключённых harness. Выбранный хост получает поручение по конкретному замечанию в новом чате проекта. В этом же меню можно скопировать поручение.

### Подключение Codex Desktop

После `npm run build` добавьте stdio-сервер в пользовательский `~/.codex/config.toml`. Укажите абсолютный путь к собранному файлу. В Windows можно использовать прямые слеши.

```toml
[mcp_servers.archiview-harness]
command = "node"
args = ["/absolute/path/to/dist/bridges/codex/server.mjs"]
env_vars = ["CODEX_APP_TOOLS_PIPE_PATH", "CODEX_APP_TOOLS_CALLER_HOST_ID", "CODEX_THREAD_ID"]
```

Откройте локальный чат в Codex Desktop и попросите вызвать `archiview_connect`. Это привяжет мост к запущенному Desktop. При запуске из терминала агента с контекстом Codex ту же привязку выполняет `node /absolute/path/to/dist/bridges/codex/server.mjs --connect`. Дальнейшие запросы из ArchiView создают отдельные чаты в выбранном проекте. Если Desktop сменил канал при перезапуске, повторите подключение.

### Подключение DeepSeek Harness

Выполните `dsh plugin --profile desktop add /absolute/path/to/dist/bridges/dsh`. Cordis регистрирует мост при активации плагина. Если профиль ещё не подхватил изменение, перезапустите профиль. Для Web-профиля укажите `--profile web`.

ArchiView и оба хоста должны работать под одним локальным пользователем и иметь доступ к файлам проекта. Мосты публикуют регистрацию в `~/.archiview/harnesses`, backend проверяет доступность по локальному IPC перед показом меню и отправкой. Переменная `ARCHIVIEW_BRIDGE_DIR` задаёт общий альтернативный каталог для изолированного запуска.

## Прототипы модулей

[Карта модулей](.archiview/modules.tree) связывает устойчивые идентификаторы с каталогами. В [контрактах](.archiview/modules) записаны назначение, роль и границы каждого модуля. У проектируемых модулей выставлен признак `archiview.prototype: true`. В пустых конечных каталогах лежит `.gitkeep`, чтобы Git воспроизводил структуру при клонировании.

Скилл [module-boundaries](skills/module-boundaries/SKILL.md) содержит правила ведения контрактов. Документы о панелях Codex и DSH в `docs/` описывают предыдущую реализацию.
