# ArchiView

Локальный просмотр архитектуры проекта: дерево модулей, структурированные
контракты arch.yaml, изменения между снимками и результаты проверок review.yaml.
Пакет также предоставляет MCP-инструменты и скилл module-boundaries.

## Панель Codex

ArchiView поставляется как локальный плагин Codex. Сборка не требует npm-зависимостей
в установленном кеше плагина:

```powershell
npm ci
npm run build:plugin
codex plugin marketplace add .
codex plugin add archiview@archiview-local
```

Откройте новый локальный чат в Codex после установки. Плагин регистрирует
приложение **ArchiView** для панели разговора и бокового меню. Если хост не
показывает точку входа автоматически, попросите открыть ArchiView: служебный
инструмент `archiview_open` возвращает UI-ресурс. Проект определяется рабочим
каталогом MCP-процесса; `--root` или `PLUGIN_ARCHITECTURE_CHANGE_VIEW_ROOT`
позволяют зафиксировать другой корень.

В панели работают те же HTML/CSS/JavaScript и HTTP backend. Дерево, поиск,
контракты, история, проверки и обновление данных не требуют вызовов инструментов
моделью. MCP используется для регистрации и открытия приложения; кнопка
**«Анализировать модуль»** передаёт явное поручение агенту хоста через MCP Apps bridge.

Кнопка доступна при полном снимке, корректном arch.yaml и поддержке отправки
сообщений хостом. Backend экспортирует входы выбранного снимка; агент анализирует
их и импортирует результат отдельной CLI-командой. Панель ждёт именно импорт,
сохраняет выбранный модуль и показывает актуальность результата отдельно от
факта завершения. Отказ передачи отображается явно и позволяет повторить действие.
Обычный запуск в браузере сохраняется; без bridge кнопка анализа отключена.

Подробности протокола, расширения области зависимостей, проверки и ограничения
описаны в [интеграции с Codex](docs/codex-panel.md). Доступность MCP Apps UI
и отправки сообщений зависит от версии хоста; установка плагина сама по себе
не подтверждает работу нативного интерфейса в текущем открытом чате.

## Запуск

Node.js 22 или новее:

~~~powershell
npm ci
npm run archiview -- --root D:/path/to/project
~~~

Адрес по умолчанию — http://127.0.0.1:4317. --port 0 выбирает свободный порт.
Сервер слушает только loopback; облачный сервис для просмотра не нужен.

Перед просмотром агент готовит контракты всего выбранного дерева по скиллу:

- Есть module.md — немедленно переносит его смысл в arch.yaml, проверяет YAML
  и удаляет старый файл. Режима совместимости для действующих контрактов нет.
- Есть оба файла — сверяет их, сохраняет принятые ограничения и удаляет module.md.
- Нет обоих — анализирует исходники, зависимости, тесты и ограничения предков,
  затем записывает содержательный arch.yaml.
- Пустой или невалидный arch.yaml — исправляет до продолжения работы.

Создание отсутствующего контракта и перенос формата входят в подготовку.
Расширение прежней ответственности согласуется с пользователем, если оно уже
не разрешено задачей. Сам просмотр не пишет исходники и не запускает скрытый ИИ.

## Просмотр

Слева — дерево с названиями модулей из arch.yaml и именами папок под ними,
поиск по пути, названию и id, фильтры изменений. При отсутствии названия
используется имя папки. Ширина дерева меняется перетаскиванием правой границы
и сохраняется в браузере. На выбранной границе работают стрелки ←/→,
Home/End задают пределы, Enter или двойной щелчок возвращает исходную ширину.
Справа:

- **Контракт**: назначение, обязанности, границы, инварианты, дополнительные поля
  и исходный YAML; ошибки схемы показываются явно.
- **Проверки**: история отчётов, отдельные оценки текущего состояния и изменения,
  полнота, наблюдаемая ответственность и результаты по каждому пункту.
- **Замечания**: категория, серьёзность, достоверность, жизненный цикл, связанные
  пункты и доказательства. Доказательство открывает сохранённый текст снимка.
- **Изменения**: построчная разница контрактов с координатами обеих версий.
- **Файлы**: собственные файлы модуля и их статусы.

| Статус | Значение |
| --- | --- |
| initial | Первый анализ без базы |
| new | Модуль появился |
| changed | Изменились собственные файлы или контракт |
| removed | Модуль отсутствует в текущем снимке |
| unchanged | Собственные файлы и контракт совпадают |

Модуль сохраняет идентичность при перемещении благодаря id. Изменения потомков
отмечаются отдельно. Статус файла не является оценкой архитектуры. Удалённый
модуль и исторические документы остаются доступны из базы.

Над деревом расположен единый выпадающий список **«Хронология»**.
Состояния перечислены от текущего к ранним:

- **Текущее состояние** — автоматически уплотнённый результат.
- **Изменение `<дата и время>`** — сохранённые состояния после HEAD, свежие сверху.
- **HEAD** — последний коммит; обновляется вместе с проектом без перезапуска.
- **Revision `<hash>`** — предыдущие коммиты из истории текущей ветки.

Новое изменение сохраняется при запуске или построении отчёта, если состояние
отличается от последнего наблюдения. Повторное обновление без правок не добавляет
точку. Изменения между двумя построениями отчёта видны как одно состояние.
Выбор точки открывает её сохранённые файлы и контракты; просмотр прошлого
не заменяет актуальный результат в work. После нового коммита локальные точки
предыдущего HEAD остаются на диске, а список показывает изменения после нового HEAD.
История коммитов идёт по первым родителям. Пункт «Загрузить ранние коммиты…»
в конце списка подгружает следующую страницу, сохраняя выбранное состояние.

Для текущего состояния в интерфейсе база Git-проекта — актуальный HEAD.
Вне Git используется сохранённая база либо начальное состояние. Для коммита
автоматически выбирается его первый родитель, для локального изменения — его HEAD.
В интерфейсе выбирается просматриваемое состояние, а базу определяет сервер.
Обновление сохраняет выбранное состояние; сохранение снимка не переключает базу.
API без параметра baseline сохраняет ранее опубликованную базу; интерфейс
передаёт baseline=auto, чтобы прежний ручной выбор не скрывал изменения после HEAD.

## Проверки и доказательства

ArchiView автоматически проверяет структуру при запуске и каждом построении
сравнения, затем уплотняет отчёты в `<root>/.archiview/work`. Структурная проверка
показывает состояние контрактов и изменения; содержательный вывод создаёт агент.

```text
.archiview/
  .gitignore
  project.json
  snapshots/                    # локальные данные, исключены из Git
    changes/
      change-<hash>.yaml         # состояния между коммитами
      .cursor.yaml              # последнее наблюдение для устранения повторов
    modules/<check-hash>/
      <module-key>.archi.yaml
      <module-key>.review.yaml
    saved-<digest>.yaml          # явно сохранённые локальные базы
  work/                         # переносимое состояние для коммита
    <module-key>.archi.yaml
    <module-key>.review.yaml
```

Имена файлов вычисляются по устойчивому id модуля. Технические данные сводятся
к текущему сравнению с выбранной базой; все реальные LLM-попытки сохраняются.
Повторный импорт той же попытки идемпотентен, коллизия id отклоняется. Предела
числа или возраста проверок нет.

Собственная актуальность, актуальность поддерева и вердикт показываются отдельно.
Изменение реализации ребёнка требует его перепроверки и меняет статус поддерева,
а повторный анализ родителя нужен при изменении его собственных входов:
кода, ограничений, композиции или используемой зависимости. Оценка текущего
состояния и оценка изменения относительно базы имеют независимую актуальность.
Неизвестное покрытие зависимостей отображается явно.

Основной список проверки содержит только собственные пункты arch.yaml выбранного
модуля, без пунктов предков и повторов одной нормы для разных версий. Совместимость
размещения подмодулей проверяется в композиции родителя. Контекст предка сам по
себе не обесценивает новую локальную проверку ребёнка; прежние отчёты сохраняют
исходную область и доказательства.

Построение без запуска HTTP-сервера:

```powershell
archiview --root D:\projects\MyProject --build-report
```

Входы содержательного ревью можно передать агенту через YAML:

```powershell
archiview --root D:\projects\MyProject --export-review-input my-module --output review-input.yaml
archiview --root D:\projects\MyProject --import-review review-input.yaml --build-report
```

Перед импортом агент заполняет модель, сведения о prompt, проверки пунктов,
выводы и доказательства. Экспорт сам по себе не является содержательной проверкой.
Зависимости задаются через `--dependencies FILE`; `--dependencies-complete`
явно подтверждает полноту их перечня. По умолчанию полнота неизвестна.

Перед коммитом добавьте исходники и `.archiview` в индекс, затем выполните:

```powershell
archiview --root D:\projects\MyProject --check-index
```

Проверяется именно подготовленный индекс Git. Команда обнаруживает различие
между staged-кодом и текущим состоянием отчёта, а также включение сырых данных.
Она не меняет индекс и не создаёт коммит. Управляемый `.gitignore` сохраняет
пользовательские дополнения; ранее отслеживаемые сырые файлы автоматически
с отслеживания не снимаются.

После клонирования достаточно `project.json` и `work`: выбранная база,
история и доказательства восстанавливаются из опубликованных YAML-файлов.
Старые v1-пакеты автоматически мигрируют с сохранением оригиналов; прежние
структурные отчёты не превращаются в LLM-проверки.

Формат и обмен с агентом описаны в [спецификации v2](docs/report-format-v2.md),
правила решения — в [документе хранения и уплотнения](docs/report-storage-and-compaction-design.md).
Подробности прежних пакетов сохранены в [спецификации v1](docs/arch-review-format-v1.md).

## MCP и скилл

~~~powershell
node src/server.mjs --root D:/path/to/project
~~~

Корень задаётся --root, PLUGIN_ARCHITECTURE_CHANGE_VIEW_ROOT или cwd процесса.
Один процесс обслуживает один проект.

| Инструмент | Вход | Результат |
| --- | --- | --- |
| module_inventory | {} | Покрытие каталогов, исходники, ошибки формата и действия подготовки |
| module_context | {"directory":"src/domain"} | Контракты от корня до каталога, включая пропуски |

Инструменты только читают. Агент анализирует код и пишет arch.yaml файловыми
средствами согласно [каноническому скиллу](skills/module-boundaries/SKILL.md),
публикуемому без изменений как skill://module-boundaries.

module_inventory возвращает schema_version, root, complete, discovery,
sourceFiles, modules, diagnostics и инструкцию preparation. Каждый модуль содержит
путь document, status, required, sourceFiles, собственные files и preparation:
ready, migrate, analyze_and_write или repair. Статусы документов: documented,
missing, empty, invalid, unreadable, migration_required. Повторяющийся id — ошибка.
Наличие документа не доказывает семантическую корректность.

В Git учитываются tracked и неигнорируемые untracked-файлы. Вне Git действует
файловый обход; произвольные .gitignore не интерпретируются. Внешние ссылки,
зависимости и типичные каталоги сборки исключены. --max-files ограничивает обход
(по умолчанию 50 000); неполнота даёт complete: false. --extension .ext расширяет
список исходных расширений MCP. Собственный arch.yaml нужен и контейнерам исходников.

Для dsh подключите этот сервер через dsh-mcp-client и добавьте его имя в servers
провайдера dsh-skill-mcp. Для Codex экспортируйте skill://module-boundaries через
codex-skill-over-mcp в .agents/skills проекта; подключение инструментов настраивается
отдельно в .codex/config.toml:

~~~toml
[mcp_servers.plugin-architecture-change-view]
command = "node"
args = ["D:/projects/dsh.plugins/plugin-architecture-change-view/src/server.mjs", "--root", "D:/path/to/project"]
~~~

В AGENTS.md закрепите обязательное применение скилла при работе с кодом и
подготовке просмотра: немедленно переносить старые контракты, анализировать и
записывать отсутствующие, соблюдать локальные и родительские границы.

## Проверка

~~~powershell
npm test
~~~

Тесты используют временные проекты, настоящий stdio MCP и HTTP. Проверяются
строгая схема, миграционные состояния, наследование, перемещения, исторические
доказательства, неизменность отчётов, устаревание и границы хранения.
