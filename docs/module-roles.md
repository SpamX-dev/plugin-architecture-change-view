# Роли модулей ArchiView

Роль отвечает на вопрос «что этот модуль обязуется делать?». Её выбирают по
`purpose` и `responsibilities` собственного контракта, сверяя выбор с
`boundaries` и `invariants`. Поле `kind` отвечает на другой вопрос: описывает
контракт модуль (`module`) или группу (`group`). Роли можно указать для обоих.

## Дерево ролей

```text
app                            — объединяет модули в приложение и отвечает за результат приложения целиком
root                           — объединяет дерево исходников и задаёт границы взаимодействия его модулей
domain                         — определяет предметные понятия и правила продукта или реализует прикладные сценарии
resources                      — определяет содержание или состав материалов, поставляемых для использования приложением, хостом или агентом
interfaces                     — способы взаимодействия с пользователем или другой системой
├── ui                         — показывает данные и принимает действия пользователя
├── cli                        — принимает команды и аргументы командной строки
├── http                       — обмен HTTP-запросами и ответами
│   ├── web-endpoints          — принимает и обрабатывает входящие HTTP-запросы
│   └── http-client            — инициирует HTTP-запросы к другому сервису
├── queue                      — обмен сообщениями через очередь
│   ├── queue-consumer         — получает и обрабатывает сообщения из очереди
│   └── queue-producer         — публикует сообщения в очередь
├── websocket                  — поддерживает обмен сообщениями через WebSocket
├── tcp                        — обслуживает соединения по TCP на уровне сокетов
├── udp                        — отправляет или принимает датаграммы UDP
└── ai                         — интерфейсы взаимодействия с агентами
    ├── mcp                    — взаимодействие по Model Context Protocol
    │   ├── mcp-server         — предоставляет инструменты, ресурсы или промпты по MCP
    │   └── mcp-client         — обращается к возможностям MCP-сервера
    └── acp                    — взаимодействие по Agent Client Protocol
        ├── acp-agent          — принимает запросы клиента и ведёт агентную сессию
        └── acp-client         — открывает сессию и передаёт запросы агенту
integration                    — подключение к внешним системам и хостам
├── integration-library        — предоставляет переиспользуемый API для работы с внешней системой
└── host-adapter               — встраивает продукт в конкретный хост и связывает их API
background-processing          — выполнение работы в фоне
├── scheduler                  — определяет, когда запускать работу
└── jobs                       — выполняет фоновые задания
data                           — представление и хранение данных
├── data-types                 — определяет структуру записей, сообщений или форматов обмена
├── serialization              — кодирует и декодирует представление данных
└── storage                    — сохраняет и читает данные приложения
migrations                     — переводит существующие данные или схему на новую версию
runtime                        — предоставляет другим модулям сведения и средства среды выполнения
builds                         — собирает и упаковывает артефакты из исходников
provisioning                   — создаёт и настраивает ресурсы среды
tools                          — предоставляет вспомогательные инструменты для работы с проектом
tests                          — проверяет поведение системы и её контрактов
```

## Запись в контракте модуля

В необязательном расширении `archiview.roles` перечисляются идентификаторы
листовых ролей. Например, если модуль обрабатывает сообщения одной очереди и
публикует результат в другую, в его контракте записывают:

```yaml
extensions:
  archiview.roles: [queue-consumer, queue-producer]
```

`queue` объединяет обе роли — перечислять его третьей меткой не нужно.
Для каждой метки укажи, какая собственная обязанность модуля её обосновывает.
Если операцию выполняет дочерний модуль, укажи роль у исполнителя. Несколько
модулей могут иметь одну роль, когда каждый выполняет свою операцию. У группы,
которая только объединяет модули, поле можно опустить.

Роль `app` подходит модулю, который объединяет части в приложение с общим
назначением и условиями поставки или запуска. Положение в корне дерева само
по себе этой роли не даёт. В ArchiView за приложение отвечает корень проекта.

Роль `root` подходит каталогу, который задаёт состав и границы дерева исходников.
Так, `src` объединяет модель проекта и адаптеры, а правило взаимодействия
позволяет MCP-серверу и dsh читать одни и те же контракты. Роль `mcp-server`
принадлежит `src/mcp`. Имя каталога и расположение прежней точки запуска сами
по себе не определяют его роль.

Метка `domain` охватывает и правила, и их применение. В ArchiView модуль
`src/snapshots` определяет, что изменилось между снимками, а `src/application`
ведёт сессию и подготавливает анализ выбранного состояния. У каждого свой
проверяемый результат. В прежних снимках прикладные сценарии могут иметь
метку `application`. При сравнении видны роли, записанные в каждом снимке.

Роль `resources` подходит владельцу скиллов, шаблонов, переводов и других
материалов продукта. Например, каталог скиллов отвечает за состав набора и
размещение умений по именам, а отдельное умение — за содержание инструкций.
Чтобы включить такой каталог в дерево, агент добавляет его в карту и записывает
обязанность и роль в контракте модуля. Само наличие `SKILL.md` не создаёт модуль.
Адаптер, который публикует готовый скилл, получает роль по своей обязанности
публикации. Источник текста остаётся в модуле скилла.

Модуль, который вызывает REST API через готовый клиент, получает `http-client`,
если исходящий запрос — его обязанность. Роль `integration-library` добавляют,
если он также предоставляет другим модулям библиотеку для работы с этой системой.
Использование TCP внутри HTTP-библиотеки роли `tcp` не даёт.

**Примеры в ArchiView.** [Самостоятельный адаптер](../.archiview/modules/archiview-http.yaml)
принимает HTTP-запросы и команды CLI: `web-endpoints`, `cli`.
[Веб-клиент](../.archiview/modules/archiview-client.yaml) показывает интерфейс и вызывает операции
двумя способами: по HTTP в самостоятельной версии и через MCP в панели хоста.
[Модуль проверок](../.archiview/modules/archiview-reviews.yaml) определяет структуру результата
(`data-types`) и правила целостности доказательств (`domain`); публикацию
результата его контракт явно отдаёт другому модулю.

В дереве видны только **заявленные** роли выбранного снимка: добавленные относительно
базы — зелёные, сохранившиеся — серые. Карточка также показывает удалённые роли
красным и зачёркивает их. Без базы сравнения все метки нейтральные. Перестановка
ролей в YAML не меняет их статус.

Соответствие кода
этим ролям — отдельный вопрос содержательной проверки. Несколько ролей сами
по себе не требуют разделения: повод обсудить границу появляется, когда за
ролями стоят независимые обязанности, которые меняются по разным причинам.
