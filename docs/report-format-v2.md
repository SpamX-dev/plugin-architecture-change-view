# YAML-отчёты ArchiView v2

Формат реализует [правила хранения и актуальности](report-storage-and-compaction-design.md).
Контракты исходников остаются arch.yaml v1. Внешний контейнер отчётов имеет
schema_version: 2; тело содержательной оценки report сохраняет структуру v1.

## Файлы и идентичность

- project.json сохраняет происхождение истории. Идентичность проекта для
  отчётов вычисляется из сохранённого происхождения, а не текущего --root.
- work/<key>.archi.yaml содержит текущее сравнение модуля и переносимые фрагменты
  выбранной базы и текущего снимка.
- work/<key>.review.yaml содержит все реальные содержательные попытки модуля.
- key — полный SHA-256 канонического строкового module_id без префикса.
- snapshots/modules/<check_hash>/ содержит локальные технические состояния
  и исходные попытки. snapshots/saved-<digest>.yaml — явно сохранённые базы.
- snapshots/changes/change-<hash>.yaml сохраняет точное состояние локального
  изменения: файлы, контракты, время, порядковый номер и baseRevision — HEAD
  на момент наблюдения. history_digest защищает также метаданные события.
  .cursor.yaml в том же каталоге хранит последнее наблюдение для устранения
  последовательных повторов. Это локальные данные, исключённые из Git.
- snapshots, прежние reviews и saved-*.json исключаются управляемым .gitignore.
  Прежние файлы остаются на диске; индекс Git не изменяется программой.

check_hash — SHA-256 входного манифеста технической проверки. Состав входов:
версия алгоритма, проект, модуль, идентичность базы и состояния модуля/поддерева,
анализатор. Новый LLM-вывод на тех же входах не меняет check_hash.
review_id отличает реальные попытки; неизменяемое содержание защищается
content_digest. registration_order сохраняет порядок регистрации независимо
от часов анализатора.

Чтение технических отчётов разрешено только для версий анализатора `1.0.1`
и `1.0.2`. Явный список `SUPPORTED_TECHNICAL_ANALYZER_VERSIONS` находится в
`src/report-store.mjs`: новые версии добавляются после проверки совместимости.
Обе поддерживаемые версии используют один обработчик технического состояния.
Он проверяет отчёт с сохранённой версией в манифесте; исходный хеш, имя и
конфигурация анализатора, состояния и снимки продолжают проверяться полностью.
Неподдерживаемая версия возвращает сообщение с её номером и списком допустимых
версий. Чтение не переписывает историю; новое построение создаёт технический
отчёт текущей версии, сохраняя содержательные проверки и выбранную базу.

## Хронология состояний

Выпадающий список «Хронология» показывает `Текущее состояние` — сжатый результат,
локальные `Изменение <дата и время>` от свежих к ранним, последний `HEAD`
и предыдущие коммиты `Revision <hash>`. Пункт «Загрузить ранние коммиты…»
подгружает следующую страницу без смены выбранного состояния.
Метаданные Git читаются страницами по цепочке первых родителей;
исходники исторического коммита загружаются только при выборе этого состояния
или базы. HEAD перечитывается при обновлении.

При запуске и построении отчёта полное новое состояние автоматически добавляется
в changes. Чистый HEAD отдельной точки не создаёт. Последовательное повторение
того же состояния не создаёт дубль, но переход A → B → A сохраняет оба события;
возврат к чистому состоянию после правок тоже остаётся событием. Неполный обход
не публикуется как завершённое изменение. Время означает момент наблюдения
ArchiView, а не время каждой записи файла.

Локальные события привязаны к HEAD. После коммита предыдущие события остаются
в snapshots, но не показываются среди изменений после нового HEAD. Они не
входят в Git; переносимыми остаются уплотнённые отчёты и сохранённые в них входы.
Произвольные прежние технические отчёты не превращаются автоматически в события:
для точного восстановления нужны полный снимок, исходное время и известный HEAD.

Выбор исторической точки задаёт target сравнения. Автоматическая база коммита —
первый родитель, база локального изменения — его baseRevision. Отдельного выбора
базы в интерфейсе нет; API сохраняет возможность явного задания baseline.
Интерфейс передаёт baseline=auto: для текущего состояния это актуальный HEAD,
вне Git — существующая сохранённая или начальная база; для исторического —
правила выше. API без baseline продолжает сохранять ранее опубликованную базу.
Исторический просмотр не публикуется вместо work:
уплотнение всегда использует фактическое текущее состояние и его выбранную базу.

## Технический отчёт

Основные поля archi.yaml:

| Поле | Значение |
| --- | --- |
| schema_version, kind | 2, archi |
| module_id, project_id | Устойчивые идентичности |
| check_hash, input_manifest | Хеш и входы технической проверки |
| baseline, current | Состояния модуля или null при его отсутствии |
| change | Существование, собственные изменения, потомки, композиция, ограничения |
| structure | Полнота и диагностика контрактов |
| publication | Версия публикации и собственные фрагменты снимков |
| review_status | Вычисленные собственные и агрегированные статусы current/change |
| storage_diagnostics | Сохранённые сообщения о неполной миграции или чтении хранилища |

Состояние включает technical, self, их отпечатки и отпечатки поддерева.
technical использует полный разобранный контракт; self — назначение, обязанности,
границы, инварианты, собственные файлы, ограничения предков и смысловые контракты
непосредственных детей. Заголовок и форматирование YAML не меняют self.
Текстовые файлы нормализуются по переводу строк; отсутствие текста/доказательств
не превращается в полную содержательную проверку.

Эта техническая проекция сохраняет происхождение прежних снимков. Новые
содержательные проверки используют локальную проекцию с `contract_scope: own`:
контекст предков не входит в собственные смысловые входы модуля. Контракты
непосредственных детей остаются входами его собственной композиции.

publication содержит generation (целый номер публикации), comparison_key
(отпечаток выбранной пары id/digest) и baseline/current. Каждая сторона — null
при отсутствии модуля или фрагмент с metadata (снимок без modules/facts),
module_index, module и facts: массивом пар index/fact. Совокупность файлов
последнего generation восстанавливает точные снимки; отсутствие фрагментов,
неправильные хеши или расхождение с техническими состояниями — ошибка.
Старая история удалённого модуля сохраняется, но не добавляет его в текущее дерево.

review_status хранит self и subtree, внутри каждой области — независимые
current/change со статусом, полнотой и диагностикой. Эти значения пересчитываются
при построении отчёта и импорте реальной попытки. storage_diagnostics сохраняется
в техническом отчёте корневого модуля; повторный запуск не дублирует сообщения.
Оба поля — производные данные публикации work: они не входят в check_hash,
не меняют исходный результат LLM и не дописываются в сырые технические отчёты.

## История содержательных проверок

Контейнер review.yaml:

```yaml
schema_version: 2
kind: review_history
module_id: example
entries: [] # Реальные попытки; пустой список не означает проверенное соответствие.
```

Каждая запись имеет kind: review, format: native-v2 или legacy-v1,
module_id, project_id, review_id, check_hash, analysis_kind, inputs, manifest,
report, baseline, current, input_digest, result_digest, content_digest.
registration_order назначается хранилищем.

Native-v2 дополнительно содержит check_manifest — исходный входной манифест
технической проверки. Валидатор проверяет его SHA-256 против check_hash, совпадение
идентичностей проекта/модуля, выбранной базы и собственного
технического состояния с сохранённой областью. Отпечаток полного технического
поддерева сохраняется в манифесте как происхождение проверки: для self-ревью
копия всей реализации потомков не требуется.

Для native-v2 baseline/current содержат только сохранённую область:
собственный модуль, нужные контракты предков и детей, объявленные зависимости
и доказательства. scoped и scope_digest фиксируют целостность этой области.
Legacy-v1 сохраняет прежний пакет целиком, чтобы не потерять исходные доказательства.

inputs содержит scope (self/subtree), независимые входы current и baseline,
baseline_identity, current_digest и change_digest. Каждый вход фиксирует
состояние модуля, разрешённые зависимости и dependency_coverage.

Новые `manifest` и `inputs` содержат `contract_scope: own`. В `manifest.contracts`
перечислены только пункты собственного arch.yaml; parent-контракты могут
сохраняться в снимке как контекст, но не добавляют обязательных проверок ребёнку.
Совпадающий собственный пункт не проверяется повторно по базовой версии: отдельная
проверка текущего кода по базовому пункту нужна при изменении или удалении пункта.
В основном списке UI показаны собственные пункты текущей версии, для удалённого
модуля — базовой. Несколько выводов по одному пункту сохраняются внутри его строки.

Отсутствие `contract_scope` означает прежнюю область `effective`: её входы,
унаследованные пункты и хеши проверяются по старым правилам. Такие записи не
переписываются; UI выделяет из них собственные пункты для основного списка.

Поддерживаемые селекторы зависимостей:

```yaml
- kind: contract
  module_id: provider
- kind: file
  path: shared/schema.yaml
- kind: api
  path: shared/public.d.ts
- kind: module
  module_id: implementation-provider
  scope: subtree
```

api означает фактический файл схемы/сигнатур. Автоматического разрешения
AST-зависимостей в ArchiView нет. Если надёжного API-файла нет, используется
реализация через file/module. Полнота перечня — явное утверждение агента;
по умолчанию dependency_coverage.status = unknown.

report хранит проверки пунктов, наблюдения, findings и независимые оценки
assessment.current / assessment.change. Для native LLM обязательны model
и prompt_digest, согласованные с manifest. Положительные проверки должны
ссылаться на сохранённые доказательства. Полное покрытие не допускает
непроверенных обязательных пунктов и неразрешённых входов.

Само изменение контракта не является замечанием и показывается только в
контракте через подсветку и диф. Не создавайте findings с kind: contract_change.
Это прежнее значение читается для совместимости с сохранённой историей;
такие записи исключаются из отображаемых замечаний, их счётчиков и действий
исправления без изменения сохранённых отчётов.

## Цикл работы агента

1. Построить отчёты: archiview --root ROOT --build-report.
2. Экспортировать входы:
   archiview --root ROOT --export-review-input MODULE_ID --output FILE.
3. При необходимости указать --dependencies DEPS.yaml. Флаг
   --dependencies-complete означает, что агент проверил полноту перечня;
   пустой список с этим флагом утверждает отсутствие используемых внешних входов.
4. Прочитать сохранённые входы и заполнить report: model, prompt_digest,
   проверки пунктов, observed, findings, assessment и ограничения покрытия.
   Указать те же model/prompt_digest в manifest; сохранить исходные входы
   и доказательства. При изменении области экспортировать её заново.
5. Импортировать: archiview --root ROOT --import-review FILE --build-report.
   Для kind: review-input CLI вычислит report.analysis.input_digest;
   хранилище сформирует остальные отпечатки и проверит связность данных.
6. Повторный импорт неизменённой попытки ничего не добавляет. Другой результат
   с тем же review_id отклоняется; новая попытка получает новый id.

Экспорт создаёт новый файл и не перезаписывает существующий. Шаблон содержит
непроверенные пункты и сам по себе не проходит как завершённый LLM-анализ.
Для миграции CLI также принимает каталог прежнего review.yaml/input.json/
current.json/baseline.json. Структурный v1-отчёт не импортируется как LLM-попытка.

## Актуальность и расхождения

| Статус | Значение |
| --- | --- |
| fresh | Проверенные входы не изменились; полнота проверки оценивается отдельно |
| stale | Известный вход изменился |
| unknown | Сравнение объявленных входов невозможно: вход недоступен, снимок неполон или формат не описывает входы |
| not_reviewed | Содержательной проверки нет |

`dependency_coverage.status: unknown` не меняет совпадение проверенных входов
на `unknown`. Оно сохраняется отдельным ограничением в `coverage` результата
актуальности и агрегированного статуса: `status: partial`, причина
`dependency_coverage_unknown`, сообщение «Полнота зависимостей не подтверждена».
Полнота также учитывает исходное `report.analysis.coverage`; импортированный
отчёт, manifest и сохранённые снимки при пересчёте не переписываются.
Таким образом, `fresh` совместим с частичным покрытием и обнаруженным нарушением.
Изменение известного входа по-прежнему даёт `stale`, независимо от полноты.

Собственная оценка и агрегация поддерева разделены. Изменение реализации ребёнка
не обнуляет self родителя, если она не использовалась в его выводе.
Изменение контракта непосредственного ребёнка меняет входы композиции родителя.
Изменение контекста предка не инвалидирует собственную проверку ребёнка.
Соответствие размещения подмодулей назначению и границам оценивается в композиции
родителя; агрегированные статусы идут вверх. Явные используемые API/контракты
зависимостей учитываются отдельно от положения каталога в дереве.
Смена базы может сделать change устаревшим при сохранении актуальности current.
В интерфейсе такая смена не скрывает результат current: исторической становится
только оценка изменения относительно прежней базы.

Несовпадающие применимые выводы показываются как конфликт, независимо от того,
какая попытка новее. Новая попытка может явно разрешить расхождение через
resolution с review_ids и reason. Целевые попытки должны относиться к той же
области и входам; ссылки проверяются, циклы запрещены. Старые записи сохраняются.

## Уплотнение, сбои и Git

При каждом запуске и построении сравнения технические данные сводятся к одной
текущей публикации. Все уникальные LLM-попытки сохраняются без TTL и численного
лимита. Повторные импорты устраняются по id и неизменяемому содержимому.
Семантическое усреднение выводов и удаление истории по размеру не выполняются.

Запись work выполняется под межпроцессной блокировкой с журналом восстановления
в snapshots. Подготовленная папка публикуется целиком. Повреждённая публикация
не заменяется молча новой. Неизвестные версии, неправильные хеши и неразрешимые
доказательства диагностируются.

Неполный baseline/current не публикуется поверх прежнего полного work.
Повторная миграция v1 сравнивает исходные report/manifest/baseline/current,
сохраняя уже записанные производные метаданные: обновление алгоритма хранилища
не создаёт новую LLM-попытку и не меняет старый результат.

После добавления исходников, project.json, .gitignore и work в Git:
archiview --root ROOT --check-index. Команда читает именно staged blobs,
проверяет данные и сравнивает текущую публикацию с подготовленным кодом.
Незастейдженные изменения не влияют на результат. Совпадение только с базой
сравнения недостаточно. Наличие сырых данных в индексе сообщается ошибкой;
команда не снимает файлы с отслеживания.

Требуются все файлы последней публикации. После клонирования без snapshots
выбранная база, проверки и доказательства доступны из work. Пересчёт использует
work как источник сохранённой истории и не стирает её из-за отсутствия raw.

YAML ограничен одним документом, строковыми уникальными ключами и обычными
типами данных. Aliases, пользовательские теги и бесконечные/NaN числа запрещены.
Ограничения захвата исходников и неполнота анализа сообщаются отдельно от
политики хранения: отсутствие лимита истории не обещает полноту любого обхода.
