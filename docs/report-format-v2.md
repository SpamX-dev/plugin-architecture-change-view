# Формат YAML-отчётов ArchiView

Формат реализует [правила хранения и актуальности](report-storage-and-compaction-design.md).
Контракты исходников используют [схему v1](arch-review-format-v1.md) и хранятся в
`.archiview/modules/<id>.yaml`. Технический отчёт имеет версию 2.
Файл результатов модуля имеет версию 3. Каждая запись в нём сохраняет формат
ReviewEntry v2 и структуру содержательной оценки report v1.

## Файлы и идентичность

- project.json сохраняет происхождение истории. Идентичность проекта для
  отчётов вычисляется из сохранённого происхождения, а не текущего --root.
- work/<key>.archi.yaml содержит текущее сравнение модуля и переносимые фрагменты
  выбранной базы и текущего снимка.
- work/<key>.analysis.yaml содержит по одному результату каждого вида анализа модуля.
- key — полный SHA-256 канонического строкового module_id без префикса.
- snapshots/modules/<check_hash>/ содержит локальные технические состояния. snapshots/saved-<digest>.yaml — явно сохранённые базы.
- snapshots/changes/change-<hash>.yaml сохраняет точное состояние локального
  изменения: файлы, контракты, время, порядковый номер и baseRevision — HEAD
  на момент наблюдения. history_digest защищает также метаданные события.
  .cursor.yaml в том же каталоге хранит последнее наблюдение для устранения
  последовательных повторов. Это локальные данные, исключённые из Git.
- snapshots, прежние reviews и saved-*.json исключаются управляемым .gitignore.
  Содержательные результаты публикуются в work.

check_hash — SHA-256 входного манифеста технической проверки. Состав входов:
версия алгоритма, проект, модуль, идентичность базы и состояния модуля/поддерева,
анализатор. Новый LLM-вывод на тех же входах не меняет check_hash.
review_id отличает реальные попытки; неизменяемое содержание защищается
content_digest. registration_order сохраняет порядок регистрации независимо
от часов анализатора.

Поддерживаются технические отчёты версий `1.0.1`, `1.0.2` и `1.1.0`.
Список `SUPPORTED_TECHNICAL_ANALYZER_VERSIONS` находится в
`analyse/module-review/technical-report.ts`: новые версии добавляются после проверки совместимости.
Все три версии используют один обработчик технического состояния.
Он проверяет отчёт с сохранённой версией в манифесте; исходный хеш, имя и
конфигурация анализатора, состояния и снимки продолжают проверяться полностью.
Неподдерживаемая версия возвращает сообщение с её номером и списком допустимых
версий. Чтение не переписывает историю; новое построение создаёт технический
отчёт текущей версии, сохраняя содержательные проверки и выбранную базу.

## Хронология состояний

Текущее состояние показывает суммарную разницу с HEAD и новые неигнорируемые
файлы. До первого коммита база пуста. Исторические коммиты сравниваются с первым
родителем. Состояния прежних локальных итераций остаются доступны по явному id.
Структура дерева, сводка статусов и подробный отчёт модуля загружаются отдельно.
Для рабочего дерева результаты читаются из текущей публикации. Для Git-коммита
отчёт и решения по замечаниям читаются из файлов выбранной ревизии. Если коммит
содержит только старые файлы или в нём нет файла модуля текущего формата,
вкладка показывает отсутствие результата.
Отчёт, впервые добавленный в следующий коммит, доступен начиная с этого коммита
при совпадении входов анализа. Просмотр Git-коммита доступен только для чтения.
Это относится и к проекту с внешним `--state-dir`. Для исторического просмотра
в коммите нужны файлы по путям репозитория `.archiview/work/` и, при наличии
решений по замечаниям, `.archiview/decisions/`.


## Технический отчёт

Основные поля archi.yaml:

| Поле | Значение |
| --- | --- |
| schema_version, kind | 2, archi |
| module_id, project_id | Устойчивые идентичности |
| check_hash, input_manifest | Хеш и входы технической проверки |
| baseline, current | Состояния модуля или null при его отсутствии |
| change | Существование, собственные изменения, потомки, композиция, ограничения |
| structure | Полнота и диагностика контрактов |
| publication | Версия публикации и собственные фрагменты снимков |
| review_status | Вычисленные собственные и агрегированные статусы current/change |
| storage_diagnostics | Сохранённая диагностика хранилища |

Состояние включает technical, self, их отпечатки и отпечатки поддерева.
technical использует полный разобранный контракт; self — назначение,
границы, инварианты, собственные файлы, ограничения предков и смысловые контракты
непосредственных детей. Заголовок и форматирование YAML не меняют self.
Текстовые файлы нормализуются по переводу строк; отсутствие текста/доказательств
не превращается в полную содержательную проверку.

Эта техническая проекция сохраняет происхождение прежних снимков. Новые
содержательные проверки используют локальную проекцию с `contract_scope: own`:
контекст предков не входит в собственные смысловые входы модуля. Объявления
непосредственных детей входят в проверку композиции. Изменение их состава или
смыслового контракта делает прежнюю оценку устаревшей. Отсутствие необходимого
контракта ограничивает проверку. Формат и хеши сохранённых входов остаются прежними. Слежение за зависимостями из LLM-отчётов отключено:
они сохраняются как происхождение доказательств и не сравниваются с текущим проектом.

publication содержит generation (целый номер публикации), comparison_key
(отпечаток выбранной пары id/digest) и baseline/current. Каждая сторона — null
при отсутствии модуля или фрагмент с metadata (снимок без modules/facts),
module_index, module и facts: массивом пар index/fact. Совокупность файлов
последнего generation восстанавливает точные снимки; отсутствие фрагментов,
неправильные хеши или расхождение с техническими состояниями — ошибка.
Отчёты удалённого модуля можно посмотреть в коммитах, в которые они вошли.

review_status хранит self и subtree, внутри каждой области — независимые
current/change со статусом, полнотой и диагностикой. Эти значения пересчитываются
при построении отчёта и импорте реальной попытки. storage_diagnostics сохраняется
в техническом отчёте корневого модуля; повторный запуск не дублирует сообщения.
Оба поля — производные данные публикации work: они не входят в check_hash,
не меняют исходный результат LLM и не дописываются в сырые технические отчёты.

## Результаты содержательных проверок модуля

Файл `work/<key>.analysis.yaml` создаётся для модуля с сохранённым результатом.
Пустой контейнер имеет следующую форму.

```yaml
schema_version: 3
kind: module_reviews
module_id: example
results: {} # Словарь записей, ключи описаны ниже.
```

| Ключ в `results` | Содержимое |
| --- | --- |
| `composition` | Опубликованный анализ композиции. |
| `implementation` | Опубликованный анализ реализации. |
| `generic` | Общий отчёт из действующего CLI-экспорта без `manifest.analysis_type`. |

Каждый ключ необязателен. После замены записи предыдущая версия файла доступна
в коммитах, которые её содержат. Если требуется сохранить промежуточный результат
между двумя анализами одного вида, включите его в коммит до замены файла.

Каждая запись имеет `kind: review`, `format: native-v2` и поля
module_id, project_id, review_id, check_hash, analysis_kind, inputs, manifest,
report, baseline, current, input_digest, result_digest, content_digest.
registration_order назначается хранилищем. Отпечатки проверяются по исходному
содержимому записи.

Для записи, в которой `resolution.review_ids` ссылается на замещённую
проверку, контейнер может содержать `resolution_inputs`. Этот
словарь связывает ID таких попыток с проверенными отпечатками их области и
входов. Тела этих попыток доступны в сохранивших их коммитах.

Native-v2 дополнительно содержит check_manifest — исходный входной манифест
технической проверки. Валидатор проверяет его SHA-256 против check_hash, совпадение
идентичностей проекта/модуля, выбранной базы и собственного
технического состояния с сохранённой областью. Отпечаток полного технического
поддерева сохраняется в манифесте как происхождение проверки: для self-ревью
копия всей реализации потомков не требуется.

Для native-v2 baseline/current содержат только сохранённую область:
собственный модуль, нужные контракты предков и детей, объявленные зависимости
и доказательства. scoped и scope_digest фиксируют целостность этой области.

inputs содержит scope (self/subtree), независимые входы current и baseline,
baseline_identity, current_digest и change_digest. Каждый вход фиксирует
состояние модуля, разрешённые зависимости и dependency_coverage.

Новый манифест использует `clause_format: purpose`. Назначение адресуется парой
`section: purpose` и `id: purpose`. Фактические обязанности с доказательствами
хранятся в `report.observed` для каждой стороны сравнения.

Новые `manifest` и `inputs` содержат `contract_scope: own`. В `manifest.contracts`
перечислены только пункты собственного контракта модуля; parent-контракты могут
сохраняться в снимке как контекст, но не добавляют обязательных проверок ребёнку.
Совпадающий собственный пункт не проверяется повторно по базовой версии: отдельная
проверка текущего кода по базовому пункту нужна при изменении или удалении пункта.
В основном списке UI показаны собственные пункты текущей версии, для удалённого
модуля — базовой. Несколько выводов по одному пункту сохраняются внутри его строки.

Поручения содержат пустой список dependencies. Полнота внешних зависимостей
остаётся неизвестной. Параметры --dependencies и --dependencies-complete CLI
отклоняет. Недостаток доказательств отражается в покрытии и not_checked.

report хранит проверки пунктов, наблюдения, findings и независимые оценки
assessment.current / assessment.change. Для native LLM обязательны model
и prompt_digest, согласованные с manifest. Положительные проверки должны
ссылаться на сохранённые доказательства. Полное покрытие не допускает
непроверенных обязательных пунктов и неразрешённых входов.

Само изменение контракта не является замечанием и показывается только в
контракте через подсветку и диф. Не создавайте findings с kind: contract_change.

## Анализ выбранного среза из вкладки модуля

Поручения из вкладок «Композиция» и «Реализация» задают `manifest.analysis_type` со значениями `composition` и `implementation` соответственно. `manifest.source_snapshot` указывает исходный срез. Экспорт содержит только текущую сторону и доказательства выбранного вида. Инструкции конкретной проверки находятся в `manifest.instructions`. Для импорта обязательны результат по каждому собственному пункту, доказательства выводов и полное покрытие заданной области. Объясните неприменимость пункта, если она следует из состава модуля. Для проверки композиции запишите классификацию непосредственных детей в `report.extensions["archiview.composition"]` согласно инструкциям в экспорте. О нехватке обязательных данных сообщите как о препятствии для выполнения анализа.

Поручения для `composition` используют анализатор `archiview-composition`.

При импорте нового результата композиции или реализации ArchiView проверяет
его входы относительно текущего рабочего дерева. Если применимость утеряна
за время анализа, импорт отклоняется. Ранее опубликованная запись остаётся
на месте, а новый анализ запускается для текущих входов.

У замечания текущего отчёта можно записать статус и решение через вкладку анализа.
Они хранятся отдельно в `.archiview/decisions/` по идентификаторам отчёта и
замечания. Включите эти файлы в коммит, чтобы зафиксировать решения вместе с
отчётом. При отсутствии решения в коммите используется статус из отчёта.

## Цикл работы агента для общего отчёта

1. Построить отчёты: archiview --root ROOT --build-report.
2. Экспортировать входы:
   archiview --root ROOT --export-review-input MODULE_ID --output FILE.
3. Не определять зависимости через LLM и не расширять экспорт параметрами
   --dependencies или --dependencies-complete. Недостаток сохранённых данных
   отражать в покрытии и not_checked.
4. Прочитать сохранённые входы и заполнить report: model, prompt_digest,
   проверки пунктов, observed, findings, assessment и ограничения покрытия.
   Указать те же model/prompt_digest в manifest; сохранить исходные входы
   и доказательства. При изменении области экспортировать её заново.
5. Импортировать: archiview --root ROOT --import-review FILE --build-report.
   Для kind: review-input CLI вычислит report.analysis.input_digest;
   хранилище сформирует остальные отпечатки и проверит связность данных.
6. Повторный импорт текущей записи с тем же review_id и содержимым идемпотентен.
   Хранилище отклоняет другое содержимое под этим идентификатором. В том же
   локальном хранилище квитанция, созданная при импорте результата текущего
   формата, подтверждает повторную обработку того же результата после его замены.
   В квитанции сохраняются только идентификатор и метаданные проверки.

Экспорт создаёт новый файл и не перезаписывает существующий. Шаблон содержит
непроверенные пункты и сам по себе не проходит как завершённый LLM-анализ.

## Актуальность результатов

Для текущего рабочего дерева собственная проверка привязана к наблюдаемой версии
модуля при фиксации входов. Наблюдатели разных версий используют общий файл
`snapshots/module-observations.json` для версий модуля, композиции и обычных исходников.
Файл `snapshots/module-observations-v2.json` также отслеживает реализацию с собственным
`SKILL.md`. Если только прежняя установка увидела промежуточные изменения и после
возврата файлов невозможно установить, затрагивали ли они реализацию навыка,
оценка получает `unknown`. Расхождение формул при одинаковых входах сохраняет актуальность.
Возврат к прежнему содержимому после замеченной
правки повышает версию. Если данные проверки не позволяют установить порядок,
совпадающие входы дают `unknown`. Открытая панель текущего состояния слушает события файловой системы и Git.
События одной серии сохранения объединяются. Наблюдаемую версию определяют
по входам модуля при очередном чтении Git. При возврате к рабочему дереву
панель заново сверяет его с HEAD.

| Статус | Значение |
| --- | --- |
| fresh | Проверенные входы не изменились; полнота проверки оценивается отдельно |
| stale | Известный вход изменился |
| unknown | Сравнение объявленных входов невозможно: вход недоступен, снимок неполон или формат не описывает входы |
| not_reviewed | Содержательной проверки нет |

Зависимости, включая неизвестную полноту или недоступность сохранённого входа,
не меняют актуальность собственных данных на `unknown` или `stale`.
Отключённое слежение сохраняется отдельным ограничением в `coverage` результата
актуальности и агрегированного статуса: `status: partial`, причина
`dependency_tracking_disabled`. Сама полнота собственного снимка по-прежнему проверяется.
Полнота также учитывает исходное `report.analysis.coverage`; импортированный
отчёт, manifest и сохранённые снимки при пересчёте не переписываются.
Таким образом, `fresh` совместим с частичным покрытием и обнаруженным нарушением.
Изменение известного входа по-прежнему даёт `stale`, независимо от полноты.

Собственная оценка родителя учитывает его код, свой контракт и совместимость
с объявленными контрактами непосредственных детей. Реализация ребёнка,
его замечания и результаты current и change относятся к самому ребёнку.
Контракты более глубоких потомков входят в проверку их непосредственных родителей.
Изменение контекста предка не инвалидирует собственную проверку ребёнка.
При проверке внутреннего модуля агент проверяет соответствие его реализации и
контракта назначению и границам предков. Их пункты не добавляются в собственный
чеклист; противоречия отражаются в findings со ссылками на ограничения предков
и доказательства. Для замечания без ссылки на собственный пункт допускаются только
границы и инварианты фактического предка из сохранённого снимка, а не соседнего модуля.
При редактировании исправляются реализация или согласованно
пересматриваются затронутые контракты; отдельный запрос анализа только фиксирует
необходимые редакции в замечаниях. Проверять всех предков из-за локальной правки не требуется.
В карточке модуля и раскрытой строке дерева видна собственная потребность в анализе.
Свёрнутая строка дополнительно транслирует агрегированный статус скрытого поддерева;
это отображение не меняет собственную оценку родителя.
Смена базы может сделать change устаревшим при сохранении актуальности current.
В интерфейсе такая смена не скрывает результат current: исторической становится
только оценка изменения относительно прежней базы.

## Публикация и Git

Поддерживаемый файл результатов имеет `schema_version: 3` и `kind: module_reviews`.
ArchiView открывает его из рабочего дерева или выбранного Git-коммита. Старые
файлы `*.review.yaml` с контейнерами `review_history`, пакеты v1 и отдельные файлы результатов в локальных
`snapshots` остаются доступны средствами файловой системы или Git. Для показа
в ArchiView нужен результат в файле текущего формата.

Запись work выполняется под межпроцессной блокировкой с журналом восстановления
в snapshots. Подготовленная папка публикуется целиком. Повреждённая публикация
не заменяется молча новой. Неизвестные версии, неправильные хеши и неразрешимые
доказательства диагностируются.

Неполный baseline/current не публикуется поверх прежнего полного work.

После добавления исходников, project.json, .gitignore и work в Git:
archiview --root ROOT --check-index. Команда читает именно staged blobs,
проверяет данные и сравнивает текущую публикацию с подготовленным кодом.
Незастейдженные изменения не влияют на результат. Совпадение только с базой
сравнения недостаточно. Наличие сырых данных в индексе сообщается ошибкой;
команда не снимает файлы с отслеживания.

Требуются все файлы последней публикации. После клонирования выбранная база,
проверки и доказательства доступны из work. За предыдущими версиями ArchiView
обращается к файлам Git-коммитов в истории этого репозитория.

YAML ограничен одним документом, строковыми уникальными ключами и обычными
типами данных. Aliases, пользовательские теги и бесконечные/NaN числа запрещены.
Ограничения захвата исходников и неполнота анализа отражаются в покрытии и диагностике.
