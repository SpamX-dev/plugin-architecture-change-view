# Хранение, уплотнение и актуальность отчётов ArchiView

Договорённости и предложения от 9 ноября 2026 года.

Документ фиксирует принятые правила реализации. Пользователь согласовал предложения
по истории и проверке родителя. Хранилище YAML-отчётов, автоматическое уплотнение
и актуальность реализованы в [формате отчётов v2](report-format-v2.md).
Прежний формат отчётов сохранён для миграции. [Контракты модулей и review.yaml v1](arch-review-format-v1.md).

Согласованы простое хранилище по модулям, автоматическое уплотнение кодом
и разделение собственных и дочерних изменений. По последнему обсуждению отчёты
хранятся в YAML; алгоритм хеша выбран ниже. Правила объёма истории и собственной
проверки родителя согласованы; заголовки предложений отражают ход проектирования.

## 1. Назначение и разделение работы

ArchiView выполняет кодом:

- сбор структуры модулей и сравнение их состояний;
- автоматическую структурную проверку при запуске и построении отчёта;
- определение актуальности сохранённых содержательных оценок;
- агрегацию изменений и статусов проверки по дереву;
- автоматическое уплотнение накопленных данных по правилам программы.

Агент реализует задачу и выполняет содержательное ревью: оценивает соответствие
кода обязанностям, границам и инвариантам. Перед изменениями он читает контракты
целевого каталога и предков, готовит отсутствующие контракты и соблюдает
согласованные границы. Действующие контракты находятся в `.archiview/modules/<id>.yaml`.

Для самого уплотнения LLM не нужна. Ранее обсуждавшаяся ручная селекция истории
агентом не является целевым механизмом. Правила первой версии зашиваются
в ArchiView; отдельного config.yaml пока не требуется. Версия правил сохраняется
в отчётах, чтобы смена алгоритма не выглядела изменением исходников.

Структурная проверка не подтверждает семантическое соответствие кода контракту.
Отсутствие формальных замечаний не создаёт положительную оценку агента.

## 2. Структура хранилища и YAML

Данные находятся в дочерней папке .archiview относительно фактического --root.
Вся папка исключается из анализа исходников, включая случай её отслеживания Git.

```text
.archiview/
  .gitignore
  project.json

  snapshots/                         # неуплотнённое локальное накопление
    changes/
      change-[hash].yaml              # полное локальное состояние после HEAD
      .cursor.yaml                   # последнее наблюдение, устранение повторов
    modules/
      [check-hash]/
        [module].archi.yaml          # результат анализа ArchiView
        [module].review.yaml         # содержательные проверки агентом

  work/                              # уплотнённое переносимое состояние для Git
    [module].archi.yaml
    [module].review.yaml
```

work — публикуемая часть данных: snapshots исключается из Git, work отслеживается.
Ранее выбранный project.json остаётся: предпочтение YAML относится к отчётам.
Он хранит идентичность проекта и сведения о формате хранилища. Перенос проекта
не меняет идентичность модулей и проверок.

Не вводим отдельные config.yaml, state.yaml, корневые папки modules, reviews,
checkpoints или универсальную базу объектов objects. Сложная ссылочная модель
и устранение всех межмодульных дублей не требуются. Дублирование допускается
как плата за простоту, в том числе в переносимом состоянии.

Для новых отчётов выбираем строгий YAML 1.2: один документ, уникальные строковые
ключи, без пользовательских тегов и aliases. Значения ограничены обычными
словарями, списками, строками, bool, null и конечными числами. Даты — строки UTC.
Неизвестная версия схемы не интерпретируется как актуальная проверка.

### Хронология в интерфейсе

Единый выпадающий список «Хронология» заменяет ленту карточек и отдельный выбор
базы. Порядок сверху вниз: `Текущее состояние` → последнее `Изменение <timestamp>`
→ предыдущие изменения → `HEAD` → предыдущие `Revision <hash>`.
Revision и HEAD обозначают коммиты; изменения — сохранённые наблюдения после
HEAD; текущее состояние — автоматически уплотнённый результат. Точки выбираются
для просмотра точных файлов, контрактов и актуальности проверок для этого состояния.
Пункт «Загрузить ранние коммиты…» в конце списка добавляет следующую страницу
истории, не переключая просматриваемое состояние.

Снимок изменения появляется при построении отчёта, когда входы изменились.
Каждое сохранение файла отдельно не отслеживается. Повторное построение без
правок не добавляет событие, возврат к предыдущему содержимому после другого
состояния добавляет. После нового коммита список показывает изменения после
нового HEAD, сохраняя прежние локальные события на диске.

Просмотр исторической точки не заменяет текущий work. Базу автоматически выбирает
сервер: для текущего состояния в Git это актуальный HEAD, для коммита — его
первый родитель, для локальной точки — её HEAD. Вне Git сохраняется существующая
сохранённая или начальная база. Интерфейс явно запрашивает режим baseline=auto;
API без этого параметра сохраняет прежнюю опубликованную базу.
Явное задание базы остаётся возможностью API, отдельного элемента выбора в UI нет.
Локальные снимки исключены из Git; в коммит входит уплотнённое состояние.

## 3. Идентичность модуля, состояния и проверки

module_id — устойчивый id из контракта модуля. Путь хранится отдельно:
перенос каталога не создаёт новый модуль, но может изменить его контекст
и применимые ограничения. Повторяющиеся id — структурная ошибка.
[module] — безопасное имя файла по этому id; точное кодирование имени остаётся
деталью формата. Путь физического корня в идентичность не входит.

### Выбранный алгоритм check-hash

[check-hash] — SHA-256 канонического манифеста технической проверки одного
модуля. Имя каталога — 64 строчных шестнадцатеричных символа без префикса.
В YAML отпечатки записываются как `sha256:<64 hex>`.

В манифест входят:

1. Домен и версия алгоритма: `archiview/module-check/v1`.
2. Устойчивая идентичность проекта и module_id.
3. Явно выбранная база: её неизменяемая идентичность и отпечатки собственного
   состояния и поддерева модуля в базе. Отсутствие базы и отсутствие модуля
   в существующей базе — разные значения.
4. Отпечатки собственного состояния и поддерева в текущем состоянии.
   Для удалённого модуля текущее состояние отсутствует.
5. Имя, версия и отпечаток настроек структурного анализатора.

Абсолютный --root, часы, mtime, случайный id запуска и результаты LLM в манифест
не входят. Текущий HEAD не заменяет отпечатки содержимого: учитываются также
незакоммиченные и новые анализируемые файлы. Выбранная Git-база разрешается
в неизменяемый commit, а не сохраняется как подвижное имя ветки.

Канонизация применяется к данным после разбора YAML. Ключи словарей сортируются
по правилу существующей функции canonical в src/serialization/digest.ts; полученный JSON
кодируется UTF-8 и хешируется SHA-256. Списки, представляющие множества входов,
предварительно сортируются лексикографически по id и относительному пути,
без зависимости от локали; значимый порядок других списков сохраняется.
Перестановка ключей, комментарии и способ кавычек YAML
не меняют отпечаток данных. JSON здесь — внутреннее представление для хеширования,
а не формат файлов отчёта.

Для текстовых исходников нормализуются CRLF/CR в LF; остальные символы,
включая пробелы и комментарии кода, сохраняются. Для бинарных входов хешируются
исходные байты. Пути относительные, с `/`, без изменения регистра. Версия
нормализации входит в алгоритм состояния.

Собственное техническое состояние включает относительный путь модуля, его
анализируемые собственные файлы, контракт и применимые ограничения. Контракт
учитывается как разобранные YAML-данные, а не повторно как сырой файл. Отпечаток
поддерева вычисляется снизу вверх из собственного состояния и отсортированных
пар «id непосредственного подмодуля — отпечаток его поддерева». Добавление,
удаление и перенос подмодуля поэтому не теряются. Это значения внутри отчётов,
а не введение отдельного хранилища объектов.

Одинаковые входы дают тот же check-hash: повторное построение не создаёт новый
каталог. Изменение потомка может изменить check-hash родителя, но само по себе
не делает собственную оценку родителя устаревшей. Её применимость определяется
другим, явным набором входов из раздела 7.

Новая LLM-попытка для тех же входов получает отдельный review_id. Несовпадающие
выводы нельзя перезаписать по совпадению check-hash. Файл [module].review.yaml внутри
каталога проверки допускает несколько таких попыток и отсутствует до первой
содержательной проверки.

check-hash удостоверяет входной манифест технической проверки, а не все байты
файлов в каталоге. Для целостности сохранённых LLM-записей и доказательств нужны
их собственные отпечатки. Добавление попытки в тот же каталог не меняет
идентичность технических входов.

## 4. Содержание двух видов отчёта

Это состав контейнеров v2; тело содержательной оценки сохраняет схему review.yaml v1.
Поля, валидация и миграция описаны в спецификации v2 и реализованы в модели отчётов.

### [module].archi.yaml

Технический отчёт содержит версию схемы и правил уплотнения, идентичность
модуля, базовое и текущее состояния, check-hash, изменения и структурные
замечания. Раздельно фиксируются:

- существование модуля в базе и сейчас: добавлен, удалён, сохранён;
- изменение его собственного кода и контракта;
- изменение состава и содержимого подмодулей;
- изменение применимых ограничений и контекста проверки;
- в work — вычисленная актуальность сохранённых оценок и причины перепроверки.

Актуальность — производная часть публикуемого отчёта: она пересчитывается
по проверкам и фактическим входам. В сыром техническом результате snapshots
сохраняются структурные данные, без выдачи статусов будущих review за результат
прошлого запуска. Новая LLM-попытка может обновить эту часть work при том же
техническом check-hash; включать чужие review-статусы в хеш ради этого не нужно.

Изменение ограничения родителя требует проверки его собственного контракта и
композиции. Само по себе оно не устаревает локальную оценку ребёнка и не меняет
метку его исходников. Исторические проверки сохраняют исходную область входов.

При уплотнении структура и итоговые изменения пересчитываются относительно
выбранной базы. Автоматическое обновление не переключает её на очередное
промежуточное состояние. Для агрегации не нужно копировать исходники всех
потомков в технический отчёт родителя.

### [module].review.yaml

Один файл содержит историю содержательных проверок модуля, а не одну усреднённую
оценку. Каждая реальная попытка сохраняет:

- review_id, время, анализатор, модель и сведения о методе анализа;
- область проверки и манифест реально использованных входов;
- отдельные отпечатки входов оценки текущего состояния и оценки изменения;
- содержательные оценки, замечания, объяснения и ограничения покрытия;
- сохранённые входы и доказательства, необходимые для понимания выводов;
- отпечатки полных входов анализа и содержательного результата.

Для оценки изменения сохраняется выбранная база и её входы. Для оценки текущего
состояния база не является обязательным входом. Отпечаток полных входов анализа
также учитывает инструкции, prompt и настройки метода: он нужен для аудита
и поиска повторов. Смена модели сама по себе не доказывает нарушение в коде.

Сохранённый вердикт не переписывается при обновлении дерева. Текущая актуальность
вычисляется отдельно; старый результат остаётся результатом для своих входов.
Если LLM ещё не запускалась для новой области, технический отчёт показывает
потребность в проверке, а не создаёт положительный вывод.

## 5. Две точки отсчёта

Изменения определяются относительно выбранной базы. Актуальность оценки агента
определяется относительно состояния, которое он действительно проверил.

```text
База B → состояние W1: модуль изменён.
Агент проверил W1: оценка актуальна для W1.
W1 → W2: код снова изменён.
Относительно B статус остаётся «изменён», но оценка W1 требует перепроверки.
```

Одного id модуля, метки «изменён», времени файла или текущего HEAD недостаточно.
Сохраняются входы проверенного состояния, с которыми сравниваются новые входы.

Для анализа следующего изменения коммит не обязателен: можно явно выбрать
сохранённое состояние как базу. Её выбор не происходит скрыто при уплотнении.

## 6. Собственные изменения и изменения подмодулей

Признаки учитываются раздельно и затем агрегируются для отображения:

| Сам модуль | Подмодули | Итоговая метка |
| --- | --- | --- |
| Без изменений | Без изменений | Без изменений |
| Изменён | Без изменений | Изменён модуль |
| Без изменений | Изменены | Изменены подмодули |
| Изменён | Изменены | Изменены модуль и подмодули |

Изменение application внутри tasks меняет поддерево tasks, даже когда собственные
файлы tasks не менялись. Добавление и удаление модулей фиксируются отдельно
от этих двух признаков. Отсутствующий в текущем дереве модуль не теряет историю.

## 7. Предложение: область проверки и её актуальность

Статусы изменения, актуальность и содержательный вердикт — отдельные
характеристики. «Требуется перепроверка» не означает «обнаружено нарушение».

### Собственная проверка, включая родителя

По умолчанию содержательная проверка относится к собственному модулю (`self`).
Её обязательные входы:

1. Собственные анализируемые файлы модуля без файлов отдельных подмодулей.
2. Его назначение, обязанности, границы и инварианты.
3. Для модуля с детьми — состав непосредственных подмодулей, их назначение,
   обязанности, границы и инварианты, необходимые для оценки композиции.
4. Контракты/API/реализация зависимостей в той мере, в которой на них
   опирается вывод; дополнительные прочитанные и использованные входы.

Контракты предков доступны как контекст размещения. Их пункты не входят в
собственный список проверок ребёнка; соответствие размещения проверяется
в композиции родителя. Чтение контекста само по себе не объявляет зависимость
от реализации всего родительского поддерева.

Таким образом, родитель проверяется на распределение ответственности,
согласованность контрактов и корректность собственного взаимодействия с детьми.
Группа без собственного кода тоже имеет такую область; она не получает
положительный вердикт автоматически.

Внутренняя реализация всех потомков не входит в self родителя по умолчанию.
Его собственный вывод условен: он предполагает соблюдение контрактов детьми.
Чтобы показать подтверждённое соответствие поддерева, нужны также актуальные
собственные проверки этих детей. Простая агрегация не заменяет их LLM-анализ.

Запрос «проверить поддерево» по умолчанию организуется как набор собственных
проверок его модулей. Если отдельно создаётся содержательный вывод с областью
`subtree`, в его входы включается всё заявленное поддерево: изменение любого
входа делает этот вывод устаревшим. Такой вывод нельзя молча выдать
за отдельные собственные проверки всех потомков.

### Входы и зависимости

Манифест содержит id модулей, относительные пути, применимые пункты контрактов,
тип использованного входа и отпечаток его содержимого. Для контрактов сравниваются
разобранные смысловые поля; изменение порядка YAML или одного title не требует
нового семантического анализа, если title не использовался как отдельный вход.
Технический отчёт при этом может показать изменение метаданных.

Контракт модуля не включается одновременно как обычный файл исходников с отпечатком
сырого текста и как смысловая проекция контракта. Для семантической актуальности
он учитывается через явно заданные поля и пункты контракта; исходный YAML можно
сохранить как материал проверки без включения его форматирования в этот отпечаток.

Для зависимости различаем опору на контракт/API и опору на реализацию:

- Если вывод опирается на контракт или опубликованный API, сохраняется именно
  этот вход: например, схема, сигнатуры, текст ограничения. Внутреннее изменение
  реализации при неизменном таком входе не обнуляет собственную оценку потребителя.
- Неизменный контракт модуля не доказывает неизменность фактического API. Если
  надёжного выделения API нет, консервативно включаем файлы реализации зависимости
  или весь её модуль. Тогда их изменение потребует перепроверки.
- Если агент использовал реализацию для вывода, она входит в область проверки,
  даже если формально был доступен более узкий контракт.
- Если полнота списка зависимостей не подтверждена, это отдельное ограничение
  покрытия с областью потенциального влияния. Сравнение проверенных входов
  остаётся самостоятельным результатом: их совпадение можно показать без
  утверждения о полноте всей системы. Недоступность явно объявленного входа
  или неполный снимок мешают сравнению и дают «актуальность не установлена».

Полный граф зависимостей не считается уже имеющимся. Первая версия может
опираться на дерево модулей, наследование контрактов и явно сохранённые входы.
Перечень прочитанных файлов сам по себе не доказывает полноту зависимостей.
Отсутствующий или неполный манифест не позволяет объявить полную актуальность.

Отпечатки зависимостей вычисляются из их входных данных, а не статусов чужих
review. Иначе циклические зависимости модулей создадут цикл пересчёта проверок.

Опора только на контракт зависимости означает условный вывод о потребителе:
он корректен при соблюдении этого контракта поставщиком. Актуальность реализации
поставщика показывается отдельно и не выводится из актуальности потребителя.
Если поставщик вне проверяемого дерева, это ограничение полного вывода о системе
остаётся видимым.

### Условия повторного анализа

| Что изменилось | Собственная проверка затронутого узла | Последствия для других узлов |
| --- | --- | --- |
| Собственный код | Требует перепроверки | Агрегированный статус идёт вверх |
| Собственное назначение или обязанности | Требует перепроверки | Перепроверяются потребители этого входа, включая композицию родителя |
| Собственная граница или инвариант | Требует перепроверки | Перепроверяются явные потребители этого входа и композиция родителя; агрегированный статус идёт вверх |
| Только контекст предка | Собственная оценка ребёнка сохраняется | Перепроверяются собственная оценка и композиция изменённого предка |
| Только реализация потомка | Сохраняется, если она не была входом self | Проверяется потомок; поддерево предков требует проверки |
| Состав или смысловой контракт непосредственного ребёнка | Родитель требует перепроверки композиции | Далее — по используемым входам и агрегации поддерева |
| Использованный контракт/API/код зависимости | Потребитель требует перепроверки | У его предков меняется агрегированный статус |
| Неподтверждённый перечень зависимостей | Известные входы сравниваются независимо | Полнота зависимостей отмечается отдельно; полный вывод о системе не подтверждён |
| Недоступный объявленный вход или неполный снимок | Актуальность не установлена | Нужны данные для сравнения; ограничение полноты остаётся видимым |
| Независимый модуль вне входов и возможного влияния | Сохраняется | Обрабатывается изменённая область |
| Только база сравнения | Оценка текущего состояния сохраняется | Оценка изменения проверяется относительно новой базы |

Изменение глубокого потомка не обязано запускать LLM на каждом предке.
Если после его ревью выявлена необходимость изменить контракт, изменение
этого контракта уже отдельно инвалидирует использующие его проверки.

Причины устаревания сохраняются раздельно: собственный код, собственный контракт,
композиция детей, вход зависимости. Исторические проверки с областью `effective`
также сохраняют сравнение унаследованных ограничений; новые проверки `own`
не включают этот контекст в локальные входы. Неподтверждённая полнота перечня
зависимостей сохраняется в ограничениях покрытия.
Признак «потомки требуют проверки» относится к агрегации,
а не автоматически к собственной оценке родителя.

### Агрегация без нового вердикта

Собственная актуальность имеет состояния: проверенные входы не изменились,
требует перепроверки, не установлена, проверки нет. Полнота проверки отображается
отдельно; неподтверждённый перечень зависимостей не отменяет факт совпадения
проверенных входов. Совпадение входов не превращает частичную проверку в полную
и не скрывает обнаруженное в проверенной области нарушение.

Статус поддерева объединяет собственные статусы узла и его потомков. Отдельно
показываются актуальные нарушения, непроверенные области и ограничения покрытия.
Один общий зелёный статус недопустим, если актуальна только self родителя.

Например:

> Собственные файлы родителя без изменений. Его проверка композиции актуальна.
> Реализация одного из потомков изменилась и требует проверки.

После проверки потомка статусы пересчитываются вверх кодом. Старая оценка
«нарушение» после изменения её входов остаётся исторической: она не считается
ни подтверждённым текущим нарушением, ни автоматически исправленным нарушением.
Если одновременно есть актуальное нарушение и непроверенная другая область,
отображаются оба обстоятельства.

Если для тех же входов сохранены несовпадающие применимые LLM-выводы, показывается
расхождение. Порядок попыток сохраняется, но уплотнение не выбирает положительный
вердикт из нескольких по удобству. До разбора расхождения единого подтверждённого
соответствия нет. Новая попытка явно разрешает расхождение через resolution
с идентификаторами прежних попыток и объяснением. Исторические результаты сохраняются.

## 8. Предложение: уплотнение без количественного лимита

Уплотнение выполняет код ArchiView при запуске и построении отчёта.
LLM и ручное определение «значимости» записей для него не нужны.

Предлагается не вводить TTL, предельное число LLM-проверок или объём,
после которого уникальная проверка удаляется. Правила первой версии:

1. В snapshots накапливаются уникальные технические состояния и реальные
   содержательные проверки. Повтор тех же технических входов использует
   прежний каталог. Автоматическое удаление уникальных сырых состояний пока
   не вводится; очистка временных файлов после успешной записи допустима.
2. В work техническая структура и изменения сводятся к текущему результату
   относительно выбранной базы, с разделением собственных и дочерних изменений.
   Все промежуточные технические состояния в work не копируются.
3. Сохраняются все реальные LLM-попытки, их входы, выводы и происхождение.
   Одинаковый вердикт на другом коде — другая проверка. Другой вывод
   на тех же входах — тоже самостоятельная запись.
4. Повторный импорт того же review_id с теми же данными идемпотентен.
   Тот же id с другим содержимым — ошибка целостности, а не замена записи.
5. Соседние попытки с полностью одинаковыми входами и содержательным результатом
   можно хранить одной группой с общим содержимым. Список review_id, время
   и порядок каждой реальной попытки сохраняются. Несоседние A → B → A
   не склеиваются через B. Совпадения одной общей метки недостаточно.
6. Повторное построение по тем же сырым записям не добавляет «проверок»,
   не увеличивает счётчики и не меняет историю. Сохраняется устойчивый порядок
   регистрации попыток; при равном времени он не выводится из часов заново.
7. Сохранённые записи work участвуют в следующем уплотнении даже после
   клонирования без snapshots. Построение только по сырым данным не должно
   стирать опубликованную историю. Удалённые модули сохраняют свои записи.

Уплотнение не означает ограниченный общий размер. Без удаления уникальных
проверок история растёт; сохранение контекста может занимать больше места,
чем сами выводы. Это осознанная цена полноты и простой модели. Если реальный
объём станет проблемой, политику удаления или архивирования обсуждаем отдельно,
а не вводим скрытое отсечение.

Технический предел чтения файла в реализации не является политикой хранения.
При превышении предела нужна явная ошибка/неполное построение, а не тихое
удаление старых записей или объявление полного отчёта.

## 9. Git, доказательства и переносимость

ArchiView формирует .archiview/.gitignore с обязательным правилом:

```gitignore
/snapshots/
```

Правила служебных временных файлов также формируются программой. Управляемый
блок обновляется с сохранением пользовательских дополнений. Сам .gitignore,
project.json и файлы work отслеживаются Git. Ignore не снимает с отслеживания
уже добавленные файлы; программа не должна молча переписывать индекс Git.

Рабочий цикл:

1. Изменения и проверки накапливаются локально; уплотнение выполняется кодом.
2. Перед коммитом подготовленный набор проверяется на целостность.
3. В коммит входят исходный код и уплотнённые данные ArchiView.
4. Неуплотнённое накопление snapshots остаётся локальным.

Предлагаемое правило сохранения доказательств: work содержит внутри своих
файлов манифесты, тексты контрактов и фактически использованный текст исходников
и контекста сохранённых LLM-проверок. Если анализировалось представление бинарного
входа, сохраняется это представление и связь с отпечатком исходных байтов.
Нельзя после удаления snapshots подменить исторический код нынешним файлом
с тем же путём. Дублирование между модулями допускается; копировать весь проект
в каждый модуль не требуется.

Ссылки на доказательства разрешаются внутри соответствующего файла review.yaml;
единственная копия нужных данных не остаётся в игнорируемой snapshots.
После клонирования доступны история, выводы и сохранённые входы, а актуальность
переоценивается по фактическому состоянию клона.

Будущая проверка перед коммитом должна проверять именно подготовленный индекс:
если код и отчёт добавлены в него из разных состояний, это нельзя выдавать
за согласованный комплект. Это проверка, а не автоматическое продвижение базы
или создание коммита. Ранее закоммиченные сырые данные обычное удаление
не убирает из истории Git.

## 10. Основные риски расхождения

| Риск | Правило, предотвращающее расхождение |
| --- | --- |
| Изменение форматирования YAML выглядит изменением смысла | Хешировать разобранные данные; текст кода нормализовать только по переводу строк |
| id модуля или общая метка «изменён» принимается за версию | Сравнивать сохранённые входы конкретной оценки |
| Общий check-hash обнуляет все оценки предков | Отдельные входы self, поддерева и оценки изменения |
| У родителя актуальна self, но всё дерево показано проверенным | Отдельно агрегировать актуальность и покрытие поддерева |
| Совпадение известных входов выдаётся за полноту всей системы | Явный API/код во входах; независимое предупреждение о неподтверждённой полноте зависимостей |
| Неизменный контракт принимается за неизменный API | Сохранять фактический API либо реализацию как вход |
| Контекст родителя ошибочно устаревает локальные проверки детей | Проверять размещение в композиции родителя, сохранять локальные входы детей и агрегировать статусы вверх |
| Новый вывод на тех же входах затирает прежний | Отдельные review_id; не перезаписывать по check-hash |
| Уплотнение теряет историю или создаёт фиктивные проверки | Сохранять реальные попытки; идемпотентно объединять только определённые повторы |
| После clone исчезают доказательства или история | work самодостаточен и входит во входы следующего уплотнения |
| Старая violation становится автоматически текущей или исправленной | Вердикт привязан к своим входам; актуальность вычисляется отдельно |
| Старый/неизвестный формат читается как новая проверка | Явные версии схемы и алгоритмов; миграция или неизвестная актуальность |

## 11. Реализация

Реализованы YAML-контейнеры v2, автоматическая структурная проверка и уплотнение,
явные входы self/subtree, независимая актуальность current/change, наследование
ограничений, зависимости и агрегация статусов. Интерфейс показывает структуру,
причины перепроверки, ограничения и расхождения выводов.

Содержательные проверки экспортируются и импортируются через YAML. История
сохраняется без количественного ограничения; повторные импорты идемпотентны.
Старые пакеты мигрируют с сохранением оригиналов и ограничения полноты их входов.
Опубликованное work участвует в последующих построениях, включая перенос без raw.

Политика записи использует межпроцессную блокировку и журнал восстановления.
CLI проверяет подготовленный индекс Git на целостность данных и соответствие
отчёта staged-коду. Подробности полей, команд и технических ограничений находятся
в [спецификации v2](report-format-v2.md). Контракт модуля использует схему v1.

Автоматическое разрешение AST-зависимостей не добавляется: используются явные
входы и заявленная полнота. Реальные ограничения захвата исходников и покрытия
отображаются; отсутствие лимита истории не отменяет этих ограничений.
