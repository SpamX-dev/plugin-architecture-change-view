# Ответственность каталогов

Открой `.archiview/modules.tree` в Git-репозитории редактируемого исходника.
У каждого репозитория рабочей папки своя карта. В обычной папке без Git и
вложенных репозиториев используется локальная карта проекта. Это плоский
YAML-словарь «устойчивый id модуля → каталог исходников». Путь задаётся
относительно корня с разделителем `/`, сам корень обозначается `.`.
Контракт по схеме v1 хранится в `.archiview/modules/<id>.yaml`. Поле `id`
совпадает с ключом карты и именем файла без расширения. Карта и контракты
хранятся в Git вместе с исходниками.

## Подготовка контрактов

1. Вызови `module_inventory`, затем передай в `module_context` путь исходника
   или каталога относительно рабочей папки, например `{"path":"server/src/main.ts"}`.
   Используй `root` из ответа как основу путей к контрактам и как корень для CLI.
   При переходе к исходникам другого репозитория запроси цепочку для нового пути.
   В DSH те же операции называются `archiview_inventory` и `archiview_context`.
   Без инструментов найди Git-корень исходника внутри рабочей папки и прочитай
   контракты из его карты по цепочке предков. Связывай id модулей с их репозиторием.
2. Если контракт отсутствует, изучи код каталога и его поддерева,
   публичные входы, зависимости, тесты и контракты предков. Добавь запись в
   карту и содержательный YAML-контракт. Имя папки и перечень файлов не
   объясняют её обязанности. Противоречивый код сам по себе не разрешает новую обязанность.
3. Исправь пустые или невалидные контракты, отсутствующие файлы, конфликтующие
   id и пути. При переносе каталога обнови его путь и пути вложенных модулей
   в карте, сохранив прежние id и имена файлов контрактов.
4. При подготовке просмотра подготовь контракты всего выбранного дерева,
   включая контейнеры исходников, тесты и скрипты. Если у каталога ресурсов есть
   собственная архитектурная обязанность, опиши её в контракте и добавь путь в карту. Это включит
   каталог в дерево, даже если в нём только инструкции или другие материалы.
   При локальном изменении кода подготовь затронутые каталоги и их предков.
   Прочитай границы предков и проверь, что изменяемый модуль им соответствует.
   Чтение контекста не требует содержательного пересмотра каждого верхнего модуля.
   Зависимости и сгенерированные результаты сборки исключаются. Не создавай
   пустые будущие каталоги.
5. Создание отсутствующего контракта на основе анализа входит
   в этот workflow и не требует отдельного подтверждения. Расширение ранее
   принятой ответственности требует согласования, если оно уже не разрешено
   текущей задачей пользователя.

## Содержание контракта v1

Обязательны schema_version: 1, id, title, kind (module или group), purpose,
responsibilities, boundaries, invariants. Последние три поля — словари
«устойчивый идентификатор пункта → строка». responsibilities содержит минимум
один пункт; boundaries и invariants могут быть пустыми словарями.
Необязательны rationale, owners и tags (массивы строк), references (массив
объектов title/uri), extensions (словарь с ключами вида organization.field).
Неизвестные поля, повторяющиеся YAML-ключи, aliases и произвольные теги запрещены.

- id уникален в проекте и сохраняется при перемещении каталога.
- Идентификаторы пунктов сохраняются при уточнении, не переиспользуются для
  другого требования. Путь берётся из карты, родитель определяется по пути исходников.
- Каждый каталог исходников имеет свой контракт. Предок не заменяет ребёнка.
  При редактировании и проверке внутреннего модуля проверь соответствие его
  реализации и контракта назначению и границам предков. Собственный чеклист
  содержит только его пункты; противоречие верхней границе отрази в замечании
  со ссылкой на ограничение предка и доказательства в проверяемом модуле.
  Исправь реализацию или согласованно пересмотри затронутые контракты, если задача
  разрешает такие изменения. Отдельный запрос анализа сохраняет исходники и
  контракты неизменными: необходимые редакции фиксируются в замечаниях.
  Изменения ребёнка, включая его контракт, сами по себе не устаревают собственную
  оценку родителя. Пересмотр верхнего контракта нужен при изменении его обещаний
  или устранении обнаруженного упущения, а не из-за самого факта локальной правки.
  Изменение контекста предка само по себе не инвалидирует локальную проверку ребёнка.
- В контракте родителя опиши общий результат в purpose, его собственные обязанности в
  responsibilities и правила взаимодействия дочерних модулей в boundaries или invariants.
  Конкретную операцию декларирует в своём контракте модуль, который за неё отвечает.
  При переносе операции между детьми контракт родителя меняется только тогда, когда меняется
  его собственная обязанность, обещанный результат или правило взаимодействия.
- При пересмотре сверь убираемые пункты с контрактами исполнителей и сохрани у владельца
  требования, которые до этого были записаны только у предка.
- Для kind: group без собственного кода укажи, какой результат даёт объединение модулей.
- Для `extensions.archiview.roles` выбирай роли по собственным обязанностям модуля.
  `domain` охватывает предметные правила и прикладные сценарии. `app` указывай,
  если модуль объединяет части в приложение и отвечает за него целиком.
  `root` указывай, когда каталог отвечает за состав дерева исходников и границы
  взаимодействия модулей. Если прежняя точка входа в корне указывает на другую роль,
  проверь её реализацию и вызывающие стороны. Зафиксируй расхождение с назначением
  каталога и при согласованном переносе обнови точки запуска вместе с контрактами.
  `resources` указывай у владельца содержания или состава поставляемых материалов.
  У каталога скиллов проверь, отвечает ли он за набор умений, у отдельного скилла —
  за текст инструкций. Сборку и публикацию ресурса описывай у их исполнителей.
  Если единственное основание для метки — операция ребёнка, оставь её у ребёнка.
  Если у группы нет собственной роли, опусти поле. При совпадении ролей проверь,
  какую отдельную операцию выполняет каждый модуль. См. [справочник ролей](../../docs/module-roles.md).
- Фиксируй устойчивые обязанности. Не включай даты, историю, TODO, проценты,
  результаты проверок, статусы реализации и перечни текущих классов и файлов.
- Не расширяй границы, чтобы оправдать уже написанное изменение.

## Снимки и проверки

ArchiView автоматически строит технические *.archi.yaml и уплотняет отчёты
в <root>/.archiview/work. Реальные содержательные попытки хранятся в
*.review.yaml с неизменяемыми входами и доказательствами; текущая актуальность
вычисляется отдельно для самого модуля, поддерева и оценки изменения.
Собственная актуальность учитывает свой код и контракт. Определение и слежение
за зависимостями через LLM отключены; определение через AST будет подключаться отдельно.
Не составляй dependencies и не подтверждай полноту их перечня. Сохранённые в прежних
отчётах списки остаются историческими данными и не инвалидируют проверки.
Контекст детей не создаёт автоматической зависимости родителя.
Потребность скрытых потомков в анализе транслируется свёрнутой строкой дерева;
раскрытая строка и карточка модуля показывают его собственный статус.
Локальные snapshots исключаются из Git. Для переноса сохраняй modules.tree,
modules/, project.json, .gitignore и work; абсолютный корень в прежних снимках является происхождением
истории, а не путём чтения исходников после переноса.

Перед содержательной проверкой экспортируй входы через
archiview --root ROOT --export-review-input MODULE_ID --output FILE.
Не передавай --dependencies и --dependencies-complete: эти параметры отключены.
Если сохранённых входов недостаточно для вывода, укажи ограничение покрытия
и not_checked вместо добавления прочитанных файлов в зависимости модуля.
Заполни модель, prompt, проверки пунктов и доказательства; импортируй через
--import-review FILE --build-report. Не меняй сохранённые входы под готовый вывод:
при изменении области экспортируй их заново. Перед коммитом выполняй --check-index
после добавления исходников и уплотнённых данных в индекс Git. Формат обмена:
plugin-architecture-change-view/docs/report-format-v2.md.
Текущее соответствие и оценка изменения — отдельные результаты. Пустой список
замечаний не доказывает успешную проверку. Непроверенные пункты обозначай
not_checked, ограничения — в analysis.coverage. Не выдавай структурную проверку
за анализ смысла кода. В ревизии Git без карты контракты отсутствуют.
Чтение контекста, тестов или потребителей не означает зависимость собственной
проверки от их реализации. Не объявляй просмотренные доказательства графом зависимостей.

## Работа с инструментами

MCP публикует этот файл как skill://module-boundaries.

- module_inventory: покрытие исходных каталогов, ошибки схемы, повторяющиеся id,
  собственные исходники и preparation: ready, analyze_and_write, repair.
- module_context: цепочка контрактов от корня репозитория до каталога, включая пропуски.
  Аргумент `path` принимает файл или каталог. Для прежних вызовов поддерживается `directory`.

Инструменты читают проект. Агент выполняет анализ и запись своими файловыми
инструментами. При недоступном сервере прочитай дерево и контракты напрямую и
продолжи подготовку. complete: false не доказывает полноту найденного дерева.
После записи повтори инвентаризацию, проверь, что карта однозначно связывает
каталоги с их контрактами.
Проверь соответствие реализации контрактам. Полная спецификация находится в
plugin-architecture-change-view/docs/arch-review-format-v1.md.
