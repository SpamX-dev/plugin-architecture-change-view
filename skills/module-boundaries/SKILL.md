# Ответственность каталогов

Структура репозитория задаёт карту системы и направляет размещение нового
кода. Организуй её так, чтобы естественное место для нового кода соответствовало
выбранной архитектуре.

## Правила компоновки директорий и файлов

1. Размещай файл с точным именем module.md в каждом каталоге с исходным кодом,
   включая вложенные каталоги и каталоги, объединяющие дерево исходников.
   Корневое описание задаёт общие границы проекта. Тесты и скрипты тоже являются
   исходным кодом; зависимости и результаты генерации или сборки исключаются.
2. Каждый module.md описывает ответственность своего каталога, её границы и
   устойчивые ограничения. Родительский документ задаёт общую область,
   дочерний уточняет её. Наличие дочернего описания не отменяет родительские
   ограничения. Опиши собственную роль каталога, не копируй родительский текст.
3. Перед изменением исходников прочитай module.md целевого каталога и цепочку
   родительских описаний до корня проекта. При перемещении прочитай границы
   исходного каталога и каталога назначения.
4. Если описания нет, изучи код и контекст задачи, затем сформулируй
   ответственность. Отделяй наблюдаемое поведение от намерения: противоречивый
   код не становится автоматически разрешённой обязанностью.
5. Когда согласованная задача требует нового архитектурного блока, создай его
   необходимую структуру и module.md с назначением и границами. Не создавай
   пустые каталоги для предположительных будущих возможностей.
6. Не включай статусы реализации, проценты готовности, TODO, даты, историю
   изменений, результаты проверок или перечень текущих классов и файлов.
   Описывай устойчивые обязанности, а не пересказ текущего содержимого.
7. Не расширяй зафиксированную ответственность ради уже написанного кода.
   Выход за границы должен быть согласован с пользователем. Если текущая
   задача уже явно разрешает конкретное изменение границы, это согласование
   достаточно; повторно его не запрашивай.
8. Поддерживай структуру как самодокументацию и ограничение: размещай новые
   сущности в соответствующем каталоге. Изменяй module.md при согласованном
   изменении ответственности, а не при каждом изменении реализации.

## Работа с MCP

Сервер plugin-architecture-change-view публикует этот скилл как
skill://module-boundaries. Имена инструментов могут иметь префикс клиента;
используй следующие имена из каталога подключённого сервера:

- module_inventory: получить каталоги дерева исходников, наличие module.md,
  пустые описания и отдельно описанные планируемые каталоги.
- module_context: прочитать описание целевого каталога и все родительские
  описания. Передай directory относительно корня проекта; для корня — ".".

Сначала вызови module_inventory для обзора покрытия, затем module_context для
каталогов задачи. Учитывай complete: false: такой результат не доказывает,
что все исходники и описания найдены. Инструменты читают проект; создавай и
редактируй module.md обычными файловыми инструментами агента.

Если сервер недоступен, прочитай документы и структуру напрямую, сообщи об
отсутствии автоматической проверки покрытия и продолжи доступную часть задачи.
Отсутствующий инструмент не отменяет локальных границ.

## Содержимое module.md

Свободная формулировка допустима, если явно определены:

- Назначение: за какой результат отвечает этот каталог.
- Границы: какие обязанности принадлежат ему и какие находятся за его пределами.
- Ограничения: устойчивые условия, которые должны сохранять изменения.

Пиши конкретно для проекта. Например, каталог инвентаря может отвечать за
хранение и перемещение предметов с атомарностью операций, а расчёт боевых
характеристик относить к другому модулю. Имя каталога само по себе не является
достаточным основанием для такой формулировки.

После изменений проверь покрытие затронутых каталогов и кратко укажи, укладывается
ли изменение в зафиксированную ответственность. Наличие файла само по себе не
доказывает соответствие кода его тексту; эвристическая оценка и история
семантических снимков относятся к отдельному этапу.
